## 一、两分钟项目介绍（可以直接讲）

我做的是一个医疗科普 RAG（检索增强生成）项目，主要解决大模型回答缺少本地资料依据、来源不容易核对的问题。系统分成离线建库、在线问答和质量评测三部分。

离线阶段，我先从本地默沙东手册 HTML（超文本标记语言）抽取正文，再加载、清洗和分块。分块采用 Small-to-Big（小块检索、大块补充上下文）：父块上限 2000 字符，子块上限 400 字符，重叠 60 字符。BGE-M3 同时生成 dense vector（稠密向量）和 sparse vector（稀疏向量），写入 Milvus。本地处理了2570篇医学主题文档，形成3936个父块和16880个子块；父子关联、类型和冗余正文已核对一致。

在线阶段，FastAPI 优先查询 Redis 缓存；无历史、来源过滤或显式策略限制时，再走 FAQ（常见问题）快通道。FAQ 未命中或被跳过后进入核心，按意图区分通用生成和医学检索。医学问题选择四种检索策略之一，正常单次融合检索最多召回16个子块，取前5个回溯父块并去重，用BGE-reranker-large对代表子块精排，最终最多2条上下文用于生成，答案与来源分字段返回。

工程上，我把问题、来源、策略和实际对话历史纳入缓存键，缓存命中也保存本轮会话；实现L0/L1/L2分层降级，按配置进行同粒度备用检索，证据不足或检索、重排故障时采用固定安全回复，生成失败时返回原文摘录。响应回传降级级别和原因，缓存仅写入及复用L0/L1回答。

评测使用Ragas，建立固定题集、独立裁判和逐题案例分析流程，分别检查证据支持、回答相关性、上下文排序与事实覆盖，保留主裁判、补评来源及完整输入。我结合逐题证据定位召回、排序和回答问题，并建立72项工程回归，覆盖文档加载、缓存语义、故障传播、评测汇总及API和界面行为；当前回归全部通过。

## 第 1 讲：入口、组件与职责

**直接讲：** 我把在线核心封装成 RAGSystem（RAG 核心编排器），负责意图、策略、检索、重排和生成；RAGWebAPI（问答接口封装）在外层增加缓存、FAQ、会话存储和评测接口。CLI（命令行界面）直接调用核心，因此它与完整 API（应用程序接口）链路的行为不同。

| 入口 | 用途 |
|---|---|
| `python main.py` | 交互问答，不经过 API 的缓存和 FAQ |
| `python main.py --data-processing --data-dir ./data/clean_md` | 离线建库；没有 `--query` 或 `--process-data` 参数 |
| `python scripts/run_offline_ingest.py` | 正式离线流水线，默认读取 `data/clean_md` |
| `python scripts/run_api.py --port 8005` | 启动 FastAPI 问答服务 |
| `web_demo/app.py` | Streamlit 问答界面 |
| `frontend/` | Vite 演示页面 |

服务启动负责加载模型、连接Milvus及按配置探测LLM连接。FAQ命中直接返回已有标准答案，省去该次问答的深通道检索与生成。CLI通过`session_id`（会话标识）保存记录，多轮API通过实际messages传入历史上下文。

## 第 2 讲：数据抽取、加载和清洗

**直接讲：** 数据处理分两层。第一层用 BeautifulSoup 抽取 HTML 正文，去掉导航、页脚、脚本等内容，输出 Markdown；第二层由入库流水线加载文本、去除页码和重复噪声、整理空白并提取 metadata（元数据）。我会特别保留数字、单位和符号，因为清洗误删这些信息会改变医疗内容的含义。

抽取脚本默认从 `data/raw/MSDZHConsumerMedicalTopics` 读取，输出到 `data/clean_md`，支持指定输入、输出目录。正式入库不会自动先执行抽取。

当前加载器支持 PDF（便携式文档格式）、DOCX、PPTX、TXT 和 MD；旧 DOC/PPT 要先转换。DOCX 同名类覆盖已修复，页码判断改成整行匹配，保留 `120/80`、`1.5` 和单字符正文；备用分块也补了不漏字、ID 唯一的回归。

文档处理的验证重点是正文完整性、数值与单位保留、块ID唯一性及父子关联。回归使用实际DOCX正文和包含医疗数值的清洗样本，检查加载、清洗与备用切分行为；数据来源与处理统计见[数据说明](data_source.md)。

## 第 3 讲：父子分块、字段与数据规模

**直接讲：** 小块容易精确匹配问题，但信息可能不完整；大块上下文更丰富，却容易混入不相关内容。所以我用子块定位证据，用父块补充上下文。子块保存 `parent_id`（父块标识）和 `parent_content`（父块正文），命中后可以直接回溯，减少二次读取；代价是冗余存储和更新一致性成本。

| 配置或字段 | 含义 |
|---|---|
| 父块 / 子块 / overlap（重叠长度） | 上限 2000 / 400 / 60 字符 |
| 切分器 | RecursiveCharacterTextSplitter（递归字符切分器），按字符计数 |
| `id` / `content` | 块标识 / 块正文 |
| `parent_id` / `parent_content` | 子块与父块的关联 / 冗余父正文 |
| `chunk_type` / `metadata` | 父子类型 / 来源等元数据 |
| 分块文件 | `data/split_docs/docs.json` |

2026-10-08本地文件复核：2570篇清洗Markdown、20816条记录，其中3936个逻辑父块、16880个子块；全部记录平均长度522.90字符，最短3、最长2000。这组数据对应本地文档与分块文件。

存量 JSON 曾把父块也标为 child（子块）。当前读取和入库按 `parent_id` 推导类型，查询联合检查标签与父 ID；本轮已备份修正磁盘JSON的3936条父标签，在线集合独立验收。父块提供较大文本窗口；父正文缺失时回退子正文。

## 第 4 讲：BGE-M3 与 Milvus

**直接讲：** BGE-M3 一次编码输出两种表示：稠密向量侧重语义相似，稀疏向量侧重词项匹配。我在 Milvus 分别检索，再通过 WeightedRanker（加权融合排序器）合并得分，兼顾换一种说法提问和关键术语匹配。

| 配置 | 当前值及理解 |
|---|---|
| dense（稠密）表示 | 1024 维；编码 `max_length=2048` token（词元） |
| sparse（稀疏）表示 | BGE-M3 的 lexical weights（词项权重）；关闭 ColBERT（多向量交互表示） |
| 稠密索引 | IVF_FLAT（倒排分簇索引），IP（内积），`nlist=256`（簇数） |
| 搜索参数 | `nprobe=16`（搜索簇数）；搜索部分簇，不是全库精确搜索 |
| 稀疏索引 | SPARSE_INVERTED_INDEX（稀疏倒排索引），IP（内积） |
| 融合权重 | sparse 0.7、dense 1.0，通过WeightedRanker融合两路候选 |
| 默认连接 | `localhost:19530`；数据库和连接别名为 `MED`，集合为 `med_msd_consumer_chunk` |
| 批量与设备 | 编码内部批量 64；`batch_process` 默认 32，正式离线脚本传 64；正式模型统一使用 CUDA（GPU 计算平台），启动校验设备可用性；向量化与重排启用 fp16（半精度浮点） |

分块长度按字符计数，模型输入按token计数。知识库稀疏检索使用BGE-M3词项权重，FAQ使用BM25（词项相关性排序算法）。离线入库通过insert写入集合；批量向量化校验输入与稠密、稀疏输出条数，稀疏词项ID与权重统一为整数、浮点类型，保证写入数据格式一致。

## 第 5 讲：Small-to-Big、重排与四种策略

**直接讲：** 正常检索先把子块过滤条件下推到 Milvus，两路融合后最多返回 16 个子块；取前 5 个，按父 ID 聚合。每个父块选择融合分最高的命中子块作为 rerank content（重排证据），与原问题一起评分，最终最多取 2 条。精排看较短的证据，生成优先看较完整的父正文。

```text
原问题 → 编码 → 稠密/稀疏检索并融合 → 最多16个子块
       → 前5个子块 → 按父ID聚合 → 代表子块精排
       → 最多2条上下文 → 生成答案和来源
```

新schema（字段结构）用`chunk_type=='child'`与非空`parent_id`联合过滤；旧结构用非空父ID过滤。异常孤立候选记录并剔除；最终按父块去重，最多保留2条上下文，来源随实际候选返回。重排分数用于候选排序。

| 策略 | 可以直接讲的解释 |
|---|---|
| direct（直接检索） | 直接用原问题检索，适合问题已经明确的情况。 |
| HyDE（假设文档嵌入） | 先生成假设答案，再用它检索；假设文本只用于找资料，不能作为证据。 |
| subquery（子问题拆分） | 把复杂问题拆开分别检索，合并去重后，用原问题统一重排。 |
| backtracking（回溯抽象） | 把具体问题改写成更一般的问题，再检索背景知识。 |

显式指定策略优先；未指定时由LLM选择，选择失败回退direct。API校验四种合法策略。HyDE和回溯使用增强后的问题检索，子问题按“子问题：”格式解析并依次检索，再按原问题统一合并和重排；解析无有效子问题时采用原问题。

16→5 是**每次检索**的限制，多个子问题合并后可能超过 5，再统一截取最多 2 条。任一路出现 error（错误）会整体升级 L2；没有错误时按有产出分支的最高降级级别合并，例如 L0+L1 标记 L1。

## 第 6 讲：FAQ、缓存与置信度

**直接讲：** API 先查 query cache（问答结果缓存）；没命中时，符合条件的请求再查 FAQ cache（常见问题缓存）和 MySQL FAQ。FAQ 用 jieba 分词和项目自写 BM25 找最多 5 个候选，先拒绝最高原始分不大于零的结果，再判断 softmax（归一化指数函数）分数是否达到 0.85。还必须核对输入与索引及数据库标准问题仅首尾空白不同、答案非空，才允许直答。其他请求进入深通道。

| 规则 | 当前行为 |
|---|---|
| query 缓存键 | `query:v3` + SHA-256（哈希摘要）；内容是问题、来源、策略、历史的 JSON（结构化序列化） |
| FAQ 缓存键 | `faq:v3` + MD5（哈希摘要）；问题仅裁剪首尾空白 |
| 字符保留 | 保留小数点、斜杠、正负号、大小写和内部空格，避免剂量混淆 |
| TTL（生存时间） | 两层默认均为 3600 秒 |
| `use_cache=false` | 同时关闭两层缓存读写，仍可查 FAQ 数据库 |
| FAQ 适用条件 | 无历史、无来源过滤、无显式策略；否则跳过 |
| 会话与降级 | 外层缓存命中也保存本轮；L2 不缓存，L1 可以缓存 |

**置信度怎么讲：** FAQ的0.85是候选softmax相对分布阈值，与最高BM25原始分大于零及标准问题一致性的条件一起控制快通道。API的`confidence`按分支返回：FAQ为固定0.95，普通RAG使用意图分类分数，L2为0；`used_cache`记录外层问答缓存命中。讲解时将匹配阈值、分类置信分数和Ragas质量指标分别说明。

`source_filter`（来源过滤）按来源字段精确匹配，使用JSON字符串转义构造表达式。来源条件同时参与检索过滤和缓存键，保证不同来源约束的回答分开存取。

## 第 7 讲：降级与生成

**直接讲：** 我把“知识库正常但没查到”和“服务发生故障”分开处理。正常子块检索为空时，L1 可以放宽过滤重新检索；命中父块后现场切成子块再重排。检索或重排故障进入 L2；默认没有证据时固定拒答，已有证据但 LLM 生成失败时返回原文摘录，并明确标记降级。

| 级别 | 当前行为 |
|---|---|
| L0（正常链路） | 子块检索、父块回溯、重排和生成 |
| L1（备用检索） | 正常空召回且允许回退时放宽过滤；取前 5 个命中，子块候选总量最多 16 |
| L2（不可正常回答） | 无召回、检索故障、重排失败或生成失败；响应附原因，不缓存 |

默认 `ALLOW_LLM_WHEN_NO_CONTEXT=False`（不允许无上下文生成）。检索 error 会拦截；无证据拒答指的是不调用**最终答案生成器**，此前选策略或 HyDE 可能已调用 LLM。重排缺模型、异常、分数数量不符、NaN（非数值）或无穷值均报错；生成前也检查空正文。生成失败的摘录最多 2 段，每段截 500 字符。

生成温度默认0.2，最大输出1024 token。Grounding（基于证据作答约束）提示词要求依据上下文、先给结论、回答有支持的部分；通用问题使用独立提示词。来源与答案分字段返回，便于调用方核对依据。

L1使用父命中分数组织备用片段，再进入统一重排。意图预测报错或返回非法类别时，核心返回L2及`intent_classifier_unavailable`原因；检索和重排故障也有对应原因字段。回归通过注入分类、检索和重排异常，核对响应及缓存行为。

## 第 8 讲：多轮、API 和可观测性

**直接讲：** MySQL 的 conversations（会话记录表）按会话保留最近 5 轮，读取与裁剪统一按时间戳和 ID 排序，避免同秒写入顺序不稳定。Streamlit 刷新后读取历史恢复界面，再把消息传给多轮接口；服务端不会仅凭会话 ID 自动加载历史。

| 接口 | 面试时可以这样说 |
|---|---|
| `POST /query` | “单轮问答接口”，支持来源、缓存开关、策略和会话标识 |
| `POST /chat` | “多轮问答接口”，从最后一条用户消息取当前问题，其余作为历史；没有策略字段 |
| `GET/DELETE /conversation/{session_id}` | “会话历史查询和清空接口” |
| `GET /health`、`GET /stats` | “组件状态、统计和降级观察接口” |
| `GET /available_strategies`、`GET /intent_example` | “支持的检索策略和意图示例接口” |
| `POST /evaluate` | “答案与上下文评测接口” |

`/chat` 的 role（角色）和 content（内容）必填，角色只允许 user（用户）/assistant（助手），内容不可空白，最后一条必须是用户；timestamp（时间戳）可选，恢复历史无需补造时间即可通过校验。响应包含答案、来源、置信分数、用时、缓存标记、意图、策略、会话及降级信息。

多轮接口从最后一条用户消息提取当前问题，其余消息作为历史。实际历史参与缓存键，最终生成提示词取最近**3个message（消息对象）**；客户端通过会话接口恢复最近5轮记录，再提交后续消息。

`response_time`记录各响应分支的处理用时：FAQ和RAG分支在会话、缓存写入前计算，外层缓存命中分支在保存会话后计算。健康和统计接口提供组件状态及进程内降级计数；日志记录查询、策略、检索结果和降级原因，便于沿处理链路定位问题。

## 第 9 讲：意图训练和 Ragas

**直接讲：** 意图模型用中文 BERT（双向编码预训练模型）微调，区分 general（通用）和 medical（医疗）。正式脚本训练 3 个 epoch（训练轮次），批量 8，预热 500 步，权重衰减 0.01，随机种子 42，按验证损失选模型，没有早停。输入最多 128 token；推理必须有训练好的分类权重，不能用随机分类头代替。

本地训练数据统计为训练集4485条、验证集499条，总计4984条，来自模板与问答数据。推理取argmax（最大分数类别），用于通用生成和医学检索分流。工程回归覆盖训练权重缺失、分类异常及非法类别，验证这些情况会返回明确的降级状态。

**评测直接讲：** 我用 Ragas 分别检查回答是否有证据、是否回答原问题，以及上下文排序和覆盖情况。理解这四项比只报一个均值更有用。

| 正式评测指标 | 关注点 | 诊断方向 |
|---|---|---|
| Faithfulness（忠实度，F） | 回答陈述是否有上下文支持 | 核查新增结论、数值与条件的证据 |
| Answer Relevancy（回答相关性，AR） | 回答反推问题与原问的相关程度 | 核查问题重点、遗漏、冗余及拒答表达 |
| Context Precision（上下文精确度，CP） | 相关上下文的排序表现 | 核查融合排名、代表子块与重排选择 |
| Context Recall（上下文召回率，CR） | 参考答案事实被上下文覆盖的程度 | 核查知识覆盖、粗召回、回溯及最终上下文 |

**优化规划参考目标：** 上下文相关性0.79（范围0.65～0.80）、召回率0.84（范围0.75～0.85）、忠实度0.89（范围0.85～0.90）、答案相关性0.89（范围0.80～0.90）。这些数值为目标设定；上下文相关性与正式CP分别定义，详细口径见[评估目标与对照方法](quality_pilot_20261010.md)。

题集保存问题、答案、上下文和参考答案，报告记录生成模型、独立裁判、指标有效数及补评来源；原始实测分数在本地留档。历史210题报告与固定20题开发对照分别保存，输入、参数和评分协议可追溯。

项目声明Ragas 0.2.6。完整参考答案集评测四项指标，仅包含问题、回答与上下文时评测F/AR。API接受`ground_truth`（标准答案）和`reference_answer`（参考答案）两种字段。实时评测关闭两层缓存并执行问答，静态评测使用给定答案与上下文；默认测试文件含5题，历史210题使用对应固定答案集。

### 一分钟介绍

### 常见追问（10题，详细答案）

#### 1. FAQ和RAG怎样配合？

我把在线问答分为标准问题快通道和医学知识检索深通道，外层首先查询Redis问答结果缓存。这个缓存键由当前问题、来源、策略和实际对话历史共同构成；在启用缓存、Redis可用且缓存回答的降级级别小于2时，直接复用答案，同时保存本轮会话。这样相同输入可以复用已有结果，不同限制条件会分别处理。

外层缓存未命中后，只有无历史、无来源过滤、无显式策略的请求才尝试FAQ。FAQ先查自身的Redis缓存，再通过jieba分词与BM25寻找最多5个标准问题候选。最高原始相关性分必须大于零，最高softmax归一化分必须达到0.85；还需输入与索引、数据库标准问题仅首尾空白不同且答案非空，符合条件时根据候选索引映射到MySQL主键，取出保存的标准答案，再回填缓存和记录会话。

FAQ未命中或因请求限制被跳过后，才调用RAG核心进行意图分类。general问题通过通用提示词直接生成；medical问题执行策略选择、混合检索、父块回溯、重排及基于上下文的生成。这个顺序使标准答案处理、检索约束和意图分流有明确职责。回归分别检查有历史、来源过滤和指定策略的请求跳过FAQ，以及缓存开关关闭两层读写的行为。

#### 2. 检索怎样支持回答？

我从文档加工阶段保留来源、父子关联和正文。子块以400字符为上限，适合定位局部事实；父块以2000字符为上限，用于补充同一段资料的上下文。BGE-M3同时生成稠密与稀疏表示：稠密表示匹配语义接近的表达，稀疏表示补充关键术语匹配，两路在Milvus中检索后通过WeightedRanker融合。

正常单次融合检索最多返回16个子块，取前5个按父ID聚合。每个父块保留融合分最高的命中子块，BGE-reranker-large用原问题与这个代表子块组成输入对，重新判断相关性。最终最多选2条上下文，L0路径主要使用对应父正文进行生成，答案与来源分字段返回，调用方可以检查资料依据。

医学提示词要求围绕问题、依据给定资料、先给结论并回答有支持的部分。程序同时检查检索结果是否可用、重排是否成功和正文是否为空；证据不足或检索、重排故障时返回带原因的安全响应。这里的工程重点是让检索依据、生成输入和最终来源可以逐步核对，排查时能区分问题出在召回、排序还是生成阶段。

#### 3. 为什么重排子块？

我将相关性判断与上下文补充分别处理。子块短，通常更集中地表达症状、疾病、检查或处理原则，与问题组成CrossEncoder输入对时，能让重排围绕实际命中证据进行判断；父块则保留前后文，适合作为生成输入。两者通过parent_id与parent_content关联，检索命中后可以直接完成回溯。

具体到L0实现，我先截取融合排名前5个子块，再按父ID去重。多个子块属于同一个父块时，保留其中融合分最高的一条作为代表，子正文放入rerank_content，父正文放入content。重排器优先读取rerank_content评分，生成器读取content补充上下文，因此同一父块既能用集中证据参与排序，也能提供较完整的资料。

例如一个父块包含疾病定义、症状和治疗原则，用户问某个症状时，命中的症状子块用于重排，父正文用于生成时理解上下文。L1备用路径则对放宽过滤后的父命中进行内存切片，以子片段进入重排与生成。回答这题时，我会明确这是实际数据流的设计目的；量化成绩单独引用对应评测集和报告。

#### 4. 重排后一定两篇？

配置TOP_K_RERANK=2表示最终最多保留2条上下文，它统计的是进入生成器的候选记录。离线处理时，一篇较长原始文档可以切成多个父块；在线检索又以父块ID为去重单位，所以两个不同父块仍可能来自同一篇文档。讲解时我会使用“最多2条上下文”来准确描述这个参数。

在L0路径中，最多16个融合候选经过前5个截取和父块去重后，可能只剩一个或几个父块。例如5个命中子块全部属于同一个父块，重排输入就只有一条；如果来自三个父块，重排后保留其中排名最高的两条。随后还会检查正文是否为空，生成器按实际可用结果拼接上下文。

子查询策略对每个子问题分别执行检索和回溯，再按文档ID合并去重，最后使用原问题统一重排。因此16→5描述每次检索的限制，最终最多2条描述统一精排后的生成输入上限。来源字段记录实际选中候选，便于区分候选数、父块数和原始文档数。

#### 5. FAQ的0.85是什么？

0.85是FAQ候选间softmax归一化分数的接受阈值。实现先对FAQ问题分词，使用BM25计算原始相关性，排序后取最多5个候选；最高原始分不大于零时直接回退。剩余候选分数先减去最大值，再计算指数及归一化，公式为p_i=exp(s_i-max(s))/Σexp(s_j-max(s))，这样可以保持数值稳定。

最高归一化分达到0.85后，还必须核对标准问题一致、答案非空，快通道才通过MySQL取答；相反人群、病程、方向及同义改写进入深通道。这个分数描述候选之间的相对优势，受候选数量与分数差影响。例如只有一个候选时，softmax值会等于1；所以代码在归一化前设置原始分大于零的检查，防止完全无词项匹配的候选因单项归一化而直接返回。

我会将三个数字分别说明：0.85是快通道匹配阈值，API中FAQ返回的confidence=0.95是该分支的固定值，Ragas指标则评估回答与证据的关系。回归覆盖零匹配、人群/病程/方向相反、否定、数值单位变化、未见词追加、缓存证据及旧缓存隔离；缓存开关回归检查关闭缓存时仍可使用数据库FAQ匹配。这样既解释公式，也能说明阈值在实际流程中的作用。

#### 6. 多轮会话怎样处理？

会话存储和模型输入分别由MySQL与messages承担。MySQL的conversations表保存session_id、问题、答案、时间戳和自增ID；每次写入后保留最近5轮，读取与裁剪统一按timestamp DESC、id DESC排序，再反转为旧到新的消息顺序，解决同秒写入时的排序歧义。

Streamlit读取会话历史后，将每轮问答转换为user和assistant消息。用户继续输入时，客户端把恢复的历史与当前问题一并提交POST /chat；服务端取最后一条用户消息作为当前问题，将其余消息作为history。role和非空content是必填内容，timestamp为可选字段，因此恢复后的消息可以直接提交。

完整请求历史参与问答缓存键，最终生成提示词截取最近3条消息。这里5轮是数据库保留数量，3条是提示词消息对象数量，两者分别控制存储和输入长度。外层缓存命中同样写入本轮问答，保证使用快通道和深通道时都能留下会话记录。HTTP回归验证恢复消息不带时间戳也可以正常请求，并检查空消息及空白问题的校验。

#### 7. 四项指标怎样解释，参考目标如何使用？

我把模型质量拆成证据支持、回答相关性、上下文排序和参考事实覆盖四个角度。F检查回答陈述能否从实际上下文得到支持；AR检查回答是否围绕用户原问题；CP关注有效上下文的排序；CR关注参考答案中的关键事实是否得到上下文覆盖。四项联合阅读，可以定位是资料缺失、召回偏离、排序选择还是生成表达的问题。

例如用户询问某种药物的起效时间，资料只说明用途，回答补充了具体小时数，我会核查新增时间是否有原文支持。若输出只是复述整段疾病介绍，则核查是否回应了时间这一问题重点。处理时先确认知识覆盖，再检查召回子块、最终父正文和输出陈述，而不是仅依据一个总分决定修改方向。

优化规划使用上下文相关性0.79、召回率0.84、忠实度0.89和答案相关性0.89作为参考目标。上下文相关性与CP分别定义；当前正式入口输出F/AR/CP/CR，报告保留各项名称、公式口径和实际有效数。参考目标服务于方案选择，逐题实测记录独立留档。

对照时固定问题、生成模型、裁判、参数和提示语言，全部样本按索引配对。评分失败记null，真实零分保留；补评只填缺失单元并记录来源。汇总保留原始精度，需要综合比较时使用同一批四项完整样本，最后展示再舍入。面试口述两位小数即可，详细报告按统一精度输出，并保留原始值供复算。

#### 8. 核心编排怎样组织？

我按组件职责组织两层。RAGSystem是问答核心，顺序执行意图分类、医学策略选择、检索与合并、重排、上下文拼接和生成，并输出answer、intent、strategy、sources及降级信息。RAGWebAPI在外层接收和校验请求，管理查询缓存、条件FAQ、会话存储、响应格式以及评测接口。

医学策略包括direct、hyde、subquery和backtracking。direct用原问题检索；HyDE先生成假设文本用于查找资料；subquery拆分问题后分别检索并合并；backtracking将具体问题改写为更一般的问题检索。外部合法策略优先，自动选择的异常回退direct，各策略统一使用父子块检索与原问题重排。

组件初始化时，API将已经创建的检索器、重排器、生成器、分类器和查询增强器传给核心复用；评测器也复用检索器的BGE-M3编码组件。这样可以保持API与CLI核心处理逻辑一致，同时让外层缓存、FAQ和持久化逻辑有独立入口。测试可以在组件边界注入结果，分别核对路由顺序、降级状态和会话行为。
