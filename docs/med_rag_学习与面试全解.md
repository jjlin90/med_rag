# med_rag 学习与面试全解（精简讲解版）

> 整理日期：2026-10-03。正文按当前实现统一口径，可直接用于面试讲解；原有 10 道常见题、27 道工程题及其追问全部保留。数据规模与评测分数来自历史留档，本次只整理文档，没有重新建库或评测。

先读第一节建立整体印象，再按第 1～9 讲理解细节；面试复习看第 11 讲，工程追问看文末题目索引。英文关键术语后附中文释义，模型和产品名称保留原名。

## 一、两分钟项目介绍（可以直接讲）

我做的是一个医疗科普 RAG（检索增强生成）项目，主要解决大模型回答缺少本地资料依据、来源不容易核对的问题。系统分成离线建库、在线问答和质量评测三部分。

离线阶段，我先从本地默沙东手册 HTML（超文本标记语言）抽取正文，再加载、清洗和分块。分块采用 Small-to-Big（小块检索、大块补充上下文）：父块上限 2000 字符，子块上限 400 字符，重叠 60 字符。BGE-M3 同时生成 dense vector（稠密向量）和 sparse vector（稀疏向量），写入 Milvus。本地历史统计是 2570 篇文件、20816 条父子块记录。

在线阶段，FastAPI 先查 Redis 缓存，再尝试 FAQ（常见问题）快通道；未命中才进入核心 RAG。核心先区分通用问题和医疗问题：通用问题直接生成，医疗问题选择检索策略。正常单次检索最多召回 16 个子块，取前 5 个回溯父块，按父 ID 去重，再用 BGE-reranker-large 对代表子块精排，最终最多 2 条上下文交给 LLM（大语言模型）生成答案，并单独返回来源。

我比较关注证据和故障处理。正常空召回可以进入备用检索，数据库或模型故障会明确标记降级；默认没有可用上下文时拒答，L2 响应不写缓存。已有证据但生成失败时，可以返回原文摘录。

评测使用 Ragas，历史 210 题四项等权均值是 0.7299，其中 Answer Relevancy（回答相关性）偏低。这个数是评测指标的综合值；后续改进需要固定题集和裁判，重新运行完整链路。项目目前还有多轮检索补全、缓存版本失效和真实并发验证等工作要做。

## 第 1 讲：入口、组件与职责

**直接讲：** 我把在线核心封装成 RAGSystem（RAG 核心编排器），负责意图、策略、检索、重排和生成；RAGWebAPI（问答接口封装）在外层增加缓存、FAQ、会话存储和评测接口。CLI（命令行界面）直接调用核心，因此它与完整 API（应用程序接口）链路的行为不同。

| 入口 | 用途 |
|---|---|
| `python main.py` | 交互问答，不经过 API 的缓存和 FAQ |
| `python main.py --data-processing --data-dir ./data/clean_md` | 离线建库；没有 `--query` 或 `--process-data` 参数 |
| `python scripts/run_offline_ingest.py` | 正式离线流水线，默认读取 `data/clean_md` |
| `python scripts/run_api.py --port 8005` | 启动 FastAPI 问答服务 |
| `web_demo/app.py` | Streamlit 问答界面 |
| `frontend/` | Vite 演示页面 |

服务启动仍需加载模型、连接 Milvus，并可能探测 LLM 连接。FAQ 命中节省的是该次问答的生成调用。CLI 的 `session_id`（会话标识）用于保存记录，不会自动恢复模型上下文。

## 第 2 讲：数据抽取、加载和清洗

**直接讲：** 数据处理分两层。第一层用 BeautifulSoup 抽取 HTML 正文，去掉导航、页脚、脚本等内容，输出 Markdown；第二层由入库流水线加载文本、去除页码和重复噪声、整理空白并提取 metadata（元数据）。我会特别保留数字、单位和符号，因为清洗误删这些信息会改变医疗内容的含义。

抽取脚本默认从 `data/raw/MSDZHConsumerMedicalTopics` 读取，输出到 `data/clean_md`，支持指定输入、输出目录。正式入库不会自动先执行抽取。

当前加载器支持 PDF（便携式文档格式）、DOCX、PPTX、TXT 和 MD；旧 DOC/PPT 要先转换。DOCX 同名类覆盖已修复，页码判断改成整行匹配，保留 `120/80`、`1.5` 和单字符正文；备用分块也补了不漏字、ID 唯一的回归。

需要继续理解的边界：OCR（光学字符识别）仍是占位；复杂表格、图片文字和通用章节恢复尚未完成。HTML 标题识别仍有固定规则，重复行清洗也需要对照原文抽样。资料源名称来自本地材料，不能据此认定每篇都已独立核验或取得再分发授权。

## 第 3 讲：父子分块、字段与数据规模

**直接讲：** 小块容易精确匹配问题，但信息可能不完整；大块上下文更丰富，却容易混入不相关内容。所以我用子块定位证据，用父块补充上下文。子块保存 `parent_id`（父块标识）和 `parent_content`（父块正文），命中后可以直接回溯，减少二次读取；代价是冗余存储和更新一致性成本。

| 配置或字段 | 含义 |
|---|---|
| 父块 / 子块 / overlap（重叠长度） | 上限 2000 / 400 / 60 字符 |
| 切分器 | RecursiveCharacterTextSplitter（递归字符切分器），按字符计数 |
| `id` / `content` | 块标识 / 块正文 |
| `parent_id` / `parent_content` | 子块与父块的关联 / 冗余父正文 |
| `chunk_type` / `metadata` | 父子类型 / 来源等元数据 |
| 分块文件 | `data/split_docs/docs.json` |

2026-09-15 本地重算：2570 个知识文件，20816 条记录，其中 3936 个逻辑父块、16880 个子块；平均长度 522.90 字符，最短 3、最长 2000。这里统计的是本地文件，实时 Milvus 行数需要另查。

存量 JSON 曾把父块也标为 child（子块）。当前读取和入库按 `parent_id` 推导类型，查询联合检查标签与父 ID；这些防护没有自动迁移旧 JSON 或已有集合。父块是较大窗口，不保证包含完整文章；父正文缺失时会回退子正文。

## 第 4 讲：BGE-M3 与 Milvus

**直接讲：** BGE-M3 一次编码输出两种表示：稠密向量侧重语义相似，稀疏向量侧重词项匹配。我在 Milvus 分别检索，再通过 WeightedRanker（加权融合排序器）合并得分，兼顾换一种说法提问和关键术语匹配。

| 配置 | 当前值及理解 |
|---|---|
| dense（稠密）表示 | 1024 维；编码 `max_length=2048` token（词元） |
| sparse（稀疏）表示 | BGE-M3 的 lexical weights（词项权重）；关闭 ColBERT（多向量交互表示） |
| 稠密索引 | IVF_FLAT（倒排分簇索引），IP（内积），`nlist=256`（簇数） |
| 搜索参数 | `nprobe=16`（搜索簇数）；搜索部分簇，不是全库精确搜索 |
| 稀疏索引 | SPARSE_INVERTED_INDEX（稀疏倒排索引），IP（内积） |
| 融合权重 | sparse 0.7、dense 1.0；是当前配置，尚无最优参数证明 |
| 默认连接 | `localhost:19530`；数据库和连接别名为 `MED`，集合为 `med_msd_consumer_chunk` |
| 批量与设备 | 编码内部批量 64；`batch_process` 默认 32，正式离线脚本传 64；自动选择 CUDA（GPU 计算平台）或 CPU，CUDA 时启用 fp16（半精度浮点） |

分块的字符上限与模型的 token 上限是两套单位。这里的稀疏检索也不同于 FAQ 的 BM25（词项相关性排序算法）。连接 alias（别名）不等于集合发布别名；当前用 insert（插入）入库，完整幂等更新、旧块清理和版本发布仍需设计。批量向量化会校验输出条数，失败会抛错，避免静默漏入库。

## 第 5 讲：Small-to-Big、重排与四种策略

**直接讲：** 正常检索先把子块过滤条件下推到 Milvus，两路融合后最多返回 16 个子块；取前 5 个，按父 ID 聚合。每个父块选择融合分最高的命中子块作为 rerank content（重排证据），与原问题一起评分，最终最多取 2 条。精排看较短的证据，生成优先看较完整的父正文。

```text
原问题 → 编码 → 稠密/稀疏检索并融合 → 最多16个子块
       → 前5个子块 → 按父ID聚合 → 代表子块精排
       → 最多2条上下文 → 生成答案和来源
```

新 schema（字段结构）用 `chunk_type=='child'` 与非空 `parent_id` 联合过滤；旧结构用非空父 ID 过滤。异常孤立候选会记录并剔除。去重后可能少于 2 条，也不保证来自两篇不同原始文档。重排分数是排序分，不是正确率。

| 策略 | 可以直接讲的解释 |
|---|---|
| direct（直接检索） | 直接用原问题检索，适合问题已经明确的情况。 |
| HyDE（假设文档嵌入） | 先生成假设答案，再用它检索；假设文本只用于找资料，不能作为证据。 |
| subquery（子问题拆分） | 把复杂问题拆开分别检索，合并去重后，用原问题统一重排。 |
| backtracking（回溯抽象） | 把具体问题改写成更一般的问题，再检索背景知识。 |

显式指定策略优先；未指定时由 LLM 选择，失败回退 direct。API 只接受四种合法策略；选择器仍是文本子串解析。HyDE、回溯成功时替换检索问题，没有自动同时融合原问题。子问题目前串行，解析依赖“子问题：”格式，无有效行回退原问，尚无明确最大子问题数。

16→5 是**每次检索**的限制，多个子问题合并后可能超过 5，再统一截取最多 2 条。任一路出现 error（错误）会整体升级 L2；没有错误时按有产出分支的最高降级级别合并，例如 L0+L1 标记 L1。

## 第 6 讲：FAQ、缓存与置信度

**直接讲：** API 先查 query cache（问答结果缓存）；没命中时，符合条件的请求再查 FAQ cache（常见问题缓存）和 MySQL FAQ。FAQ 用 jieba 分词和项目自写 BM25 找最多 5 个候选，先拒绝最高原始分不大于零的结果，再判断 softmax（归一化指数函数）分数是否达到 0.85。通过才直答，否则进入 RAG。

| 规则 | 当前行为 |
|---|---|
| query 缓存键 | `query:v2` + SHA-256（哈希摘要）；内容是问题、来源、策略、历史的 JSON（结构化序列化） |
| FAQ 缓存键 | `faq:v2` + MD5（哈希摘要）；问题仅裁剪首尾空白 |
| 字符保留 | 保留小数点、斜杠、正负号、大小写和内部空格，避免剂量混淆 |
| TTL（生存时间） | 两层默认均为 3600 秒 |
| `use_cache=false` | 同时关闭两层缓存读写，仍可查 FAQ 数据库 |
| FAQ 适用条件 | 无历史、无来源过滤、无显式策略；否则跳过 |
| 会话与降级 | 外层缓存命中也保存本轮；L2 不缓存，L1 可以缓存 |

**置信度怎么讲：** FAQ 的 0.85 是候选间相对分布，一个正分候选也会得到 1，还需要独立正负样本校准。API 的 `confidence`（置信分数）同样没有统一答案概率含义：FAQ 固定返回 0.95，普通 RAG 使用意图分类分数，L2 为 0。`used_cache`（使用缓存标记）只反映外层缓存命中，FAQ 内层命中也可能是 false。

`source_filter`（来源过滤）只做来源精确匹配，已用 JSON 字符串转义构造表达式，不是权限控制。缓存还缺知识库、模型和 prompt（提示词）版本失效机制，更新后可能在 TTL 内继续返回旧答案。

## 第 7 讲：降级与生成

**直接讲：** 我把“知识库正常但没查到”和“服务发生故障”分开处理。正常子块检索为空时，L1 可以放宽过滤重新检索；命中父块后现场切成子块再重排。检索或重排故障进入 L2；默认没有证据时固定拒答，已有证据但 LLM 生成失败时返回原文摘录，并明确标记降级。

| 级别 | 当前行为 |
|---|---|
| L0（正常链路） | 子块检索、父块回溯、重排和生成 |
| L1（备用检索） | 正常空召回且允许回退时放宽过滤；取前 5 个命中，子块候选总量最多 16 |
| L2（不可正常回答） | 无召回、检索故障、重排失败或生成失败；响应附原因，不缓存 |

默认 `ALLOW_LLM_WHEN_NO_CONTEXT=False`（不允许无上下文生成）。检索 error 会拦截；无证据拒答指的是不调用**最终答案生成器**，此前选策略或 HyDE 可能已调用 LLM。重排缺模型、异常、分数数量不符、NaN（非数值）或无穷值均报错；生成前也检查空正文。生成失败的摘录最多 2 段，每段截 500 字符。

生成温度默认 0.2，最大输出 1024 token。Grounding（基于证据作答约束）通过提示词要求依据上下文、先给结论、只回答有支持的部分；通用问题有独立提示词。来源与答案分字段返回，没有逐句强制引用对齐。

理解边界：提示词不是程序级事实验证；召回候选不代表证据足够。L1 片段沿用父命中分数，截断可能丢掉后面证据，开销也未必小于 L0。初始化失败可能直接阻止服务启动，不能由请求级降级推出全链路可用保证。意图预测报错目前仍以 medical（医疗）和 0 分兜底，没有专用故障标记。

## 第 8 讲：多轮、API 和可观测性

**直接讲：** MySQL 的 conversations（会话记录表）按会话保留最近 5 轮，读取与裁剪统一按时间戳和 ID 排序，避免同秒写入顺序不稳定。Streamlit 刷新后读取历史恢复界面，再把消息传给多轮接口；服务端不会仅凭会话 ID 自动加载历史。

| 接口 | 面试时可以这样说 |
|---|---|
| `POST /query` | “单轮问答接口”，支持来源、缓存开关、策略和会话标识 |
| `POST /chat` | “多轮问答接口”，从最后一条用户消息取当前问题，其余作为历史；没有策略字段 |
| `GET/DELETE /conversation/{session_id}` | “会话历史查询和清空接口” |
| `GET /health`、`GET /stats` | “组件状态、统计和降级观察接口” |
| `GET /available_strategies`、`GET /intent_example` | “支持的检索策略和意图示例接口” |
| `POST /evaluate` | “答案与上下文评测接口” |

`/chat` 的 role（角色）和 content（内容）必填，角色只允许 user（用户）/assistant（助手），内容不可空白，最后一条必须是用户；timestamp（时间戳）可选，恢复历史无需补造时间即可通过校验。响应包含答案、来源、置信分数、用时、缓存标记、意图、策略、会话及降级信息。

模型提示词只取最近 **3 个 message（消息对象）**，不是 3 轮。历史参与缓存与最终生成，但意图、策略和检索没有历史补全；例如“它怎么治疗”仍可能检索不准。

`response_time`（响应用时）在 FAQ/RAG 分支的会话和缓存写入前计算，不是完整端到端时延。降级计数在进程内，重启清零，多 worker（工作进程）不会自动聚合。路由虽然写成 async（异步），内部仍有同步推理和 IO（输入输出）；generate_stream（流式生成）尚未接入 API/界面，SSE（服务端事件推送）未打通。统计还可能触发模型连接探测，健康状态也不等于完整依赖可用。

## 第 9 讲：意图训练和 Ragas

**直接讲：** 意图模型用中文 BERT（双向编码预训练模型）微调，区分 general（通用）和 medical（医疗）。正式脚本训练 3 个 epoch（训练轮次），批量 8，预热 500 步，权重衰减 0.01，随机种子 42，按验证损失选模型，没有早停。输入最多 128 token；推理必须有训练好的分类权重，不能用随机分类头代替。

2026-09-15 重算训练集 4485 条、验证集 499 条，总计 4984。数据主要来自模板，构造脚本还读取测试问答，因此需要另建独立真实问题集，检查混淆矩阵和医疗漏分率；现有材料不足以支持准确率 100%。当前直接取 argmax（最大分数类别），没有低置信度澄清机制。

**评测直接讲：** 我用 Ragas 分别检查回答是否有证据、是否回答原问题，以及上下文排序和覆盖情况。理解这四项比只报一个均值更有用。

| 指标 | 关注点 | 历史分数 / 有效数 / GLM与DeepSeek条数 |
|---|---|---|
| Faithfulness（忠实度，F） | 回答陈述是否有上下文支持 | 0.8163 / 210 / 202+8 |
| Answer Relevancy（回答相关性，AR） | 回答反推问题与原问的相关程度 | 0.5007 / 210 / 205+5 |
| Context Precision（上下文精确度，CP） | 相关上下文的排序表现 | 0.8405 / 210 / 206+4 |
| Context Recall（上下文召回率，CR） | 参考答案事实被上下文覆盖的程度 | 0.7619 / 210 / 206+4 |
| 四项等权平均 | 上述四项的算术平均 | 0.7299 |

报告是 `data/test_query/eval_ragas_210_grounded_v3_ar_mixed_complete.json`：历史生成模型为 GLM-4.5-air，主裁判 GLM-4.6V，缺项由 DeepSeek-v4-flash 补评，并保存逐项来源。它不是修复后重测，也不是每题多个裁判的同题实验。旧基线 0.525 的链路和裁判不同，不能把差值直接归因给某一项优化。F 不保证原文正确，AR 不是医学准确率，CR 也不是全库 Recall@K（前K项召回率）。

项目声明 Ragas 0.2.6。正式四指标需要整批每条都提供非空参考答案；否则只跑 F/AR。API 接受 `ground_truth`（标准答案）和 `reference_answer`（参考答案）两种字段。实时评测关闭两层缓存，静态评测只评已给出的答案和上下文；默认测试文件只有 5 题，不会自动复现 210 题报告。

评测失败记 null（缺失值），真实零分保留；均值按有效值算，没有有效值时也为 null，同时展示 valid_counts（有效评分数）和 complete_count（完整样本数）。全 NaN 的已知指标列保留。fallback（备用裁判）是自定义 F/CP/AR，必须与正式 Ragas 分开；合并报告统一引擎、四项完整有限分数、去重和统计分母，并报告剔除数。

**如何改进：** 我会固定题集、生成模型和裁判，抽查 AR 低分的 badcase（失败样例），区分检索偏离、答非所问、遗漏和冗余，再逐项改动并配对复评，同时看 F 与有效数。只对固定上下文重生成能检验生成层；验证整个系统需要重新检索和生成。

## 第 11 讲：面试表达与追问

### 一分钟介绍

这是一个医疗科普 RAG（检索增强生成）系统。我用 400/2000 字符父子分块，让小块负责精确检索、大块提供上下文；BGE-M3 输出稠密和稀疏表示，在 Milvus 混合检索，再用 BGE-reranker-large 精排，正常单次流程是最多 16 个子块、取前 5 个回溯、最终最多 2 条上下文生成。API 外层有 Redis 缓存和 MySQL FAQ 快通道，核心有通用/医疗意图分类、四种检索策略和三级降级。历史 210 题四指标均值是 0.7299，目前 AR 偏低。我重点改进过缓存语义、故障传播和评测缺失值处理，后续还要补多轮检索改写和同口径质量验证。

### 常见追问（原有 10 题全部保留）

1. **为什么不全用 FAQ？** FAQ 适合覆盖固定标准问题；未覆盖或带历史、来源、策略约束的问题进入 RAG。节省多少调用需要统计实际命中率。
2. **为什么不直接用大模型？** 我用检索提供本地依据，并返回来源，方便检查答案。实际质量仍取决于召回、证据相关性和生成约束。
3. **为什么重排子块？** 较短证据便于判断与问题的相关性，父正文用于补上下文。当前 L0 给每个父块的最佳命中子块打分，实际增益需要消融实验验证。
4. **重排后一定两篇？** 最多两条上下文；去重或候选不足会更少，而且可能来自同一原始文档。
5. **FAQ的0.85是什么？** 最多 5 个候选的 softmax（归一化指数函数）阈值，是相对分布，没有校准为答案正确概率。
6. **会话为什么存了还可能答不好？** 当前历史已进入缓存键和生成提示，但检索前没有补全指代。“它怎么治疗”这类问题仍可能查错资料。
7. **指标0.7299是什么？** 历史 F、AR、CP、CR 四项等权平均，有不同裁判补缺的记录，不能解释为医学准确率。
8. **项目是不是Multi-Agent？** 当前是 RAG 编排与 LLM 策略选择，没有 Multi-Agent（多智能体）调度、A2A（智能体间通信）、MCP（模型上下文协议）或 LangGraph（图式工作流框架）状态图实现。
9. **有生产性能数据吗？** 当前没有足够证据支持固定 QPS（每秒请求数）、P95（第95百分位延迟）、显存开销或 SLA（服务等级协议）。这些需要指定硬件和负载压测。
10. **数据授权是否核验？** 本地材料标记为默沙东大众版来源；目前没有逐篇来源和再分发授权的完整验证记录。
