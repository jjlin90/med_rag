med_rag 混合检索与父子块链路（Small-to-Big）

BGE-M3 一次编码产双向量 → Milvus 两路并行召回 → WeightedRanker 加权融合 → 子块定位、父块作答 → CrossEncoder 精排 Top-2 → 送 LLM。

三个最容易被追问的技术点

Q：为什么 sparse 用 BGE-M3 自带的稀疏向量，而不是传统 BM25？
BM25 是统计式词权——只看词频和逆文档频率，不理解语义，也无法处理"未登录词"。BGE-M3 的 sparse 是模型学习出来的词权，能识别一句话里哪些token真正重要。典型场景："1型糖尿病"和"2型糖尿病"字面高度重合、语义完全相反，纯 dense 容易把它们拉到一起，靠 sparse 把 "1型"/"2型" 的权重顶起来才能分开。
Q：WeightedRanker 和 RRF 的区别？0.7 / 1.0 是拍脑袋吗？
RRF 只利用排名，丢掉了分数强度信息；WeightedRanker 是先把两路分数各自归一化，再按权重加权，量纲问题由 Milvus 内部处理，所以不需要自己写 min-max。0.7 / 1.0 是对齐 EduRag 的初始值、按医疗语料人工调过的，不是理论最优——诚实的说法是"在自建 200 条医疗 QA 上做过网格搜索粗调，dense 主导、sparse 补充"，如果面试官追问 A/B 数据，就承认没做严格显著性检验。
Q：为什么必须两阶段（双塔召回 + CrossEncoder 精排）？
双塔把 query 和 doc 分别编码成向量，doc 向量可离线预计算，检索时只做一次向量近邻搜索，能扫全库 2 万条；代价是 query 和 doc 之间没有任何交互，精度有限。
CrossEncoder 把 query 和 doc 拼成一个序列送进 Transformer 做全交互，精度高得多；代价是必须在线计算，无法预编码——对 2 万条全算一次要几分钟，不可能用于召回。所以只能"召回放宽到 16 条，精排收到 2 条"。这是工业界标准范式，不是设计缺陷。

面试会追问的坑（含已修复项）

  • 🟢 父块是不是也进向量库了？会不会被检索到？ 在库里，但检索不到。库里 20816 条 = 子块 16880 + 父块 3936（父块占 18.9%）。
    最初子块过滤在应用层后置，父块会先占用 Top-K 名额再被丢弃，实测槽位浪费率 25%；且原代码有条"挑不出子块就返回父块"的降级分支，会让 Small-to-Big 静默失效。
    修法：把过滤下推到 Milvus。关键点——Milvus 只能对顶层标量字段下推 expr 过滤，JSON 内部的 key 用不了，所以给 schema 加了顶层 chunk_type 字段。旧库无该字段时自动退化为 parent_id != ""（语义等价），因此两万条数据不用重建。同时删除了静默降级分支，改为记录 ERROR。
  • 父块 2000 字会不会稀释向量语义？ 会。这正是 Small-to-Big 要解决的问题：用 400 字子块做检索（语义聚焦），回溯 2000 字父块做生成（上下文完整）。
  • 召回算的是子块分，精排算的是父块分，这不是两批文档吗？ 是的，这正是 Small-to-Big 的精髓——中间换过一次粒度。子块分高说明"这个位置相关"，父块提供"这个位置周围的完整论述"。父块分数由其最高分子块继承。
  • Top-2 父块 = 最多 4000 字，会不会超上下文？ 约 4000 字符对通义千问的上下文窗口没有压力，但 token 成本翻倍，且稀释注意力。这是"上下文完整"和"信噪比"之间的取舍。
  • 🟢 检索不到的时候怎么办？会降级返回 2000 字父块吗？ 不会，这条路径已被永久禁止、没有开关。
    删掉静默降级后，链路演进为 L0 / L1 / L2 分层降级，原则是「降级路径必须比主路径更安全，而不是更粗糙」：
    L0 下推过滤只召回子块，orphan 父块记 ERROR 剔除（400 字子块 → 2000 字父块）；
    L1 子块召回为空时放开过滤重查，命中父块后现场切成 400 字子块——换的是检索入口，输出粒度不退化，下游无需写特例；
    L2 仍为空或基础设施故障时安全拒答、不调用 LLM（医疗场景里无依据硬答是最高风险行为），且故障导致的降级不写缓存，避免空结果污染故障恢复后的请求。
