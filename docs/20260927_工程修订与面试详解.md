## 一、当前端到端流程

### 1. 离线链路怎样真正运行

原始 MSD HTML 的抽取与正式入库是两条命令。`scripts/extract_msd.py` 默认从 `data/raw/MSDZHConsumerMedicalTopics` 读取章节索引与 HTML，输出到 `data/clean_md`；允许显式指定输入、输出目录。入库脚本不会替用户先执行抽取，也不能由输出目录存在就推断原始数据完整。

正式入库按加载、清洗、元数据增强、父子分块、保存分块、向量化、Milvus 写入执行。父块上限 2000 字符、子块上限 400 字符，两级 overlap 为 60；这是字符数配置，既不是 token 数，也不保证每条实际长度都等于上限。BGE-M3 同时输出 1024 维稠密向量和稀疏词权，关闭 ColBERT。存量父块误标不会因为代码变更自动从磁盘消失：本次修复了读取、写入和查询时的防护，没有擅自重建真实集合。

当前 DOCX 基本文本读取已经修复。OCR 仍是占位；旧二进制 DOC/PPT 从扩展名支持表移除，避免用户误以为 python-docx/python-pptx 能直接读取。扫描件、复杂表格和图片中的医疗信息仍需另行实现和验收。

### 2. 在线请求的准确顺序

`POST /query` 校验非空问题及合法策略；`POST /chat` 从最后一条 user 消息取当前问题，其余消息形成 history。两者进入同一编排。先按问题、来源、策略、历史构造 query:v2 缓存键。缓存命中后也保存本轮会话。

未命中时，只有没有历史、没有来源过滤、没有显式策略的请求才进入 FAQ 快通道。FAQ 先在允许缓存时查 faq:v2，再检查 MySQL/BM25；原始最高分不大于零则回退 RAG，正分候选按最多 5 条计算 softmax，达到 0.85 才允许取答案。`use_cache=false` 会关闭两层读写，并不关闭 FAQ 数据库检索本身。

深通道做一次 general/medical 分类。general 使用独立的一般知识提示词，不套“只能引用所给医学上下文”的空上下文约束；medical 根据指定策略或模型选出的 direct、hyde、subquery、backtracking 检索。稠密/稀疏两路融合最多 16 条，正常链路取前 5 个子块、按 parent_id 聚合，用代表子块重排，最终最多 2 条上下文进入生成。最终 sources 与 answer 分字段返回，目前没有答案句子与证据的自动内联绑定。

### 3. 成功、空结果和故障的区别

没有命中不是数据库故障。L0 的子块检索正常但为空时，可以开启 L1，放宽子块限制后把命中父块在内存切成子块，再参与重排。L1 的“同粒度”只说明上下文粒度，没有证明质量、延迟或风险与 L0 等同。

Milvus 或向量化发生异常时，底层不再吞掉错误；Retrieval 记录 error，Small-to-Big 标记 L2。任一子查询分支出现基础设施错误也升级整体 L2。重排失败、空重排上下文、答案生成失败同样明确标记降级。默认没有可用上下文时拒答；在有依据但答案生成不可用的情况下，可以返回原文摘录。level>=2 不写 query 缓存，避免服务恢复后继续提供故障期间的结果。

## 二、修复专题与面试追问

### 问题 1：缓存已经用了哈希，为什么仍会答错？

**回答要点：** 哈希只负责把输入编码成键，不能判断输入是否保留了语义。旧实现先删除标点和空格，再计算 MD5，于是 `1.5mg` 和 `15mg` 在哈希之前就已经变成同一个字符串。这是预处理造成的确定性碰撞，换成 SHA-256 但沿用同样的预处理仍然无法解决。

**当前实现：** 仅删除首尾空白，保留小数点、斜杠、正负号、单位大小写、内部空格。query 使用结构化序列化后的 SHA-256；FAQ 保持 MD5，但同样保留语义字符并升级 v2 命名空间。哈希算法不是本次正确性修复的核心，输入语义和缓存维度才是。

**追问：为什么要 v2？** 如果修复后继续读取旧命名空间，旧错误答案仍可能在 TTL 内命中。新命名空间让旧条目自然过期，无需清空用户的整个 Redis 数据库。

### 问题 2：缓存键需要哪些维度？一定要包含 session_id 吗？

**回答要点：** 缓存键应涵盖会改变答案的输入。当前包含 question、source_filter、strategy、history；同一句“这个药可以吗”在不同历史下含义可能完全不同，同一问题限制不同来源也不能复用结果。

session_id 是存储会话的标识，不一定是生成内容的完整描述。两个不同 session 可能提供相同历史；同一 session 的历史会不断变化。因此本次用实际 history，而不是仅加 session_id。现在请求缓存保存完整请求 history，即使生成提示词只取最后几个消息，也会更保守地分开缓存。

**追问：知识库更新怎么办？** 目前键未加入知识库版本、模型版本与 prompt 版本，这是后续可做的版本化失效设计。上线前需要确定更新策略；不能把本次“隔离请求上下文”说成解决了所有缓存新鲜度问题。

### 问题 3：为什么缓存命中还要写会话？

缓存节省的是重复检索和生成，而用户确实完成了新一轮交互。旧实现命中直接返回，界面当时能看到答案，刷新后却无法从 MySQL 恢复这一轮；后续审计也缺失记录。

修复后，返回缓存结果前仍执行 update_session_history。测试用记录调用的模拟存储，确认 session_id、question、answer 与本轮一致。这证明 API 编排调用了存储，不等于证明真实数据库在任何故障下都成功写入。数据库不可用时仍会降级，需要由运维观测识别。

### 问题 4：FAQ 的 0.85 能不能说成 85% 准确率？

不能。softmax 描述同一候选列表中的相对分布；它依赖候选数量和分数间距，没有使用独立的正确/错误标签进行概率校准。只有一个候选时，无论正分很小还是很大，softmax 都为 1。原实现甚至允许零分单候选得到 1，本次先拒绝最高原始分<=0，消除了“完全无词项匹配也满分”的明确漏洞。

**追问：正分就足够了吗？** 不足够。相邻疾病、否定表达、不同剂量、同一实体的不同问题仍可能只部分匹配。应建立正负样本，衡量快通道错误直答率、覆盖率和转深通道比例，再选择绝对分、相似度、词项覆盖或额外验证条件。不能在没有数据的情况下任意增加阈值并宣称已经安全。

### 问题 5：为什么有历史或 source_filter 时跳过 FAQ？

当前 FAQ 检索只看问题字符串，不理解 history，也不应用 Milvus 的 source_filter，更不会按指定的检索策略生成答案。如果用户要求某个来源，快通道却直接返回另一个来源的标准答案，即使文本相关也违背了请求。

本次选择在这些请求上直接走深通道，减少不符合约束的回答。显式 strategy 同理：指定 hyde 表示调用方希望执行该策略，不能先返回 FAQ 并把策略选择绕过。未来若给 FAQ 增加来源元数据和上下文判定，可以重新设计适用条件；目前不冒充已经实现。

### 问题 6：为什么不能把检索异常当成空列表？

空列表可能代表“服务正常但知识库没有资料”，也可能代表“服务已经断开”。如果底层把异常变成空列表，上层既无法正确告警，也可能错误地进入备用检索，甚至调用模型补答。

当前边界是：Milvus SDK 的异常向上传播；Embedding 推理失败也抛异常。Retrieval.search 保留现有列表返回接口，同时通过 status.error 输出错误；Small-to-Big 将其转换成携带水位与原因的 RetrievalResult。这样既保持部分旧调用兼容，又让主问答链路区分 no_recall 与 retrieval_error。

**追问：测试有没有真的连数据库？** 没有。测试调用真实 MilvusStore.search、真实 Retrieval.search 和 search_child_to_parent，只在 SDK 客户端边界注入异常，因此验证的是应用层故障传播，不是服务部署与网络配置。

### 问题 7：子查询一部分成功，为什么整体仍然拒答？

如果一个复杂问题被拆为多个方面，其中一部分因为服务故障未检索成功，另一部分的文档不一定足以回答原问题。旧逻辑取有产出分支中最低水位，可能得到 level=0 但 error 非空，最终将部分失败的结果当正常答案缓存。

当前策略把任一 error 升级为 L2，默认整体拒答。代价是可用性更保守，但错误状态不会丢失。正常空召回与异常仍有区别：某个分支正常查到空结果，不一定使另一正常分支的证据失效。没有 error 时，合并中 L0 与 L1 同时存在按最高有产出水位标记 L1，不再隐藏降级。

**追问：能做部分回答吗？** 可以另行设计，但必须显式标明未覆盖子问题、证据对应关系、失败原因以及缓存策略。目前没有这些机制，因此不能把它说成已经完成的能力。

### 问题 8：为何重排失败也要对调用方可见？

重排是决定哪些证据进入生成的重要步骤。旧代码异常时直接按融合分原顺序返回，用户和健康指标看不出精排已经失效。取到文档不代表整个证据筛选流程成功。

当前 reranker 在模型不可用、计算异常、分数数量不符、出现 NaN/无穷值时显式报错；RAG 编排返回 reranker_unavailable 的 L2 响应，跳过答案生成和缓存。即使调用方替换了 reranker 并返回空列表，生成前还有一次正文检查，避免把“未找到相关知识”当成可用证据继续生成。

### 问题 9：DOCX 加载为什么看起来没有报错却没有内容？

模块导入了 python-docx 的 Document，随后又声明了用于统一文档对象的同名类。运行时全局名称已经指向后者；调用 Document(file_path) 缺少 metadata 参数，异常又被加载器捕获并转换为空结果。

本次将外部工厂命名为 DocxDocument，内部统一 Document 保持原名。测试不是简单 mock 一个返回值，而是真正生成临时 DOCX、写入包含 `1.5mg` 的正文、重新加载并检查内容。它能覆盖工厂调用和基本正文读取，但未覆盖所有 Office 格式和复杂排版。

### 问题 10：文本清洗为什么需要数值回归？

医疗正文中的数字、小数、斜杠和单位往往承载核心事实。旧页码模式使用 re.search，在整行中找到 `120/80` 就删除整行；纯符号判定只识别中英文，数字行也被误删。清洗后语句可能仍然通顺，因此仅观察日志或统计文档数很难发现内容损坏。

当前页码模式只做整行匹配，取消无标签数值比值的页码规则；保留数字和单字符有效内容。测试同时包含应保留的 `120/80`、`1.5`、`5`、包含页码文字的正文，以及应删除的纯页码/分隔线。

**追问：是否证明清洗完全无损？** 没有。重复行规则、HTML 结构丢失、表格提取仍可能产生问题。应补原文与清洗结果的差异抽样，以及数值和单位保留率指标。

### 问题 11：备用分块为什么也会影响数据正确性？

备用实现不仅要“能运行”，还要保证正文不漏、ID 不重复、父子关系可追溯。旧备用路径接收父 Chunk 却读取不存在的 page_content；用偏移除以 chunk_size 生成 ID，在 overlap 存在时可能重复；切到标点后仍按原固定步长前进，可能跳过一段正文。

当前根据对象类型读取 content/page_content，按真实窗口序号命名，子块 ID 包含父块 ID，备用切分按固定字符窗口覆盖全文。配置初始化时拒绝负 overlap 或 overlap>=块大小。回归检查全文字符覆盖、子块长度和 ID 唯一性，避免“成功运行但悄悄丢内容”。

### 问题 12：修复 chunk_type 就等于修复历史知识库吗？

不等于。代码、磁盘 JSON 与正在运行的 Milvus 集合是三个不同状态。当前读取旧分块时按 parent_id 恢复类型，入库时同样按父子关系写顶层标签，查询新 schema 时联合检查 chunk_type 与非空 parent_id，降低误标父块挤占 Top-K 的影响。

这些措施没有自动改写磁盘历史 JSON，也没有重建或覆盖 Milvus。真正的数据迁移需要备份、校验父子 ID 关系、写入新版本集合、检查数量与抽样召回，再明确切换读流量。本文不会把这些后续动作写成已执行。

### 问题 13：向量化为什么不能失败一批就继续？

若生成函数返回空数组，后续 zip 会静默产出零条；日志仍可能显示某批已经处理，最终得到部分入库的知识库。如果丢的是某类长文，还会产生系统性的覆盖偏差。

当前推理异常直接传播；batch_process 校验 dense、sparse 与输入条数相同，失败时停止而不掩盖缺失。稀疏字典的 token ID 转为 int、权重转为 float，减少 SDK 类型兼容风险。已完成的历史批次如何断点恢复仍是独立工程设计，本次没有添加事务性全库重建能力。

### 问题 14：timestamp 为什么改成可选？

服务端历史恢复接口只返回 question/answer，前端将其重建为 role/content，并没有原始时间戳。原 /chat 模型把 timestamp 设为必填，导致刷新恢复后再发消息出现 422，而从未刷新的新会话可能正常，形成状态相关故障。

timestamp 当前不参与问题、历史提示或检索语义，强制要求它没有必要。因此改为可选，保留对带时间戳客户端的兼容。role 则收紧为 user/assistant，内容不可空白，最后一条必须是 user。测试通过实际 HTTP 测试客户端走序列化与校验链路。

### 问题 15：为什么同秒历史要增加 id 排序？

数据库使用 DATETIME 与 NOW()，快速写入的两条记录可能时间相同。只按 timestamp DESC 排序不保证相同时间记录的稳定顺序；在保留最近五轮时，读出的顺序和被删除的记录可能不一致。

读取与裁剪都增加 id DESC，形成确定顺序，再反转为旧到新的历史。这处理了时间精度导致的排序歧义，并没有解决所有并发事务问题。多 worker、连接池和事务隔离仍需要真实数据库并发测试。

### 问题 16：general 分支为什么需要单独提示词？

general 的定义是不检索医学知识库、回答一般知识。但旧实现复用了“只能基于相关医学知识回答”的严格 grounding 提示词，同时传空 context，行为目标冲突。

当前一般知识分支传独立 system_prompt，医学分支保留原 grounding 规则。如果 LLM 没有返回答案，一般知识分支也标记 L2，避免把“无法生成”作为正常结果缓存。分类器把医疗问题错分为 general 的风险并未由提示词修复彻底消除，仍应通过真实意图测试集与保守路由策略验证。

### 问题 17：评测失败为什么不能记 0？

零分是一种有效观察，例如回答完全不切题；接口超时、配额耗尽、解析失败则代表没有观察值。将失败写成 0 会混淆模型质量与评测基础设施可靠性，拉低均值，也让不同运行的失败率污染比较。

当前 fallback 解析失败、缺项、非有限值、越界分数记 null；有效均值仅纳入成功评分，真实 0 保留。完整率和 valid_counts 同时输出。如果某指标没有任何有效评分，其均值是 null，前端显示“未评出”。比较模型时还需报告缺失率并分析缺失是否随机；不能只排除失败后挑更好看的均值。

### 问题 18：整列 NaN 为什么必须保留？

如果请求四指标而只成功得到三项，删除全 NaN 列会使 metrics 看起来像本来就只有三项；完整样本数也可能在缩小后的指标集合上被高估。

当前已知指标列即使全 NaN 也保留，逐项值为 null，有效数为 0，完整行数按实际列集合计算。整次 Ragas 异常仍可进入明确标识的 fallback，但“某列失败”不会悄悄等同于“这列不存在”。后续仍需区分请求的指标集合、引擎实际返回列和输入是否提供标准答案。

### 问题 19：为什么不能拿 fallback 的 CP 与 Ragas CP 混算？

同一个名字不保证同一种测量程序。fallback 是单次提示词给分，正式 Ragas 有各自指标定义和执行方式；无标准答案时正式路径只请求 F/AR，而 fallback 仍可能输出三个自定义分数。

当前并行和接力汇总只收正式 ragas 引擎、四项有限分数齐全的样本，并接受真实全零。缺少任一项仍需补评，不能因为某个指标>0 就把整行标成完成。旧报告中的零分是否曾被用于表示失败，需要结合历史日志判断，不能靠本次代码反推来源。

### 问题 20：评测页面修了什么，验证到什么程度？

旧页面读取 context_relevance、answer_relevance、success，后端返回的是 context_precision、answer_relevancy、complete_count 等字段。错误被默认 0 隐藏，导致页面能渲染却展示错误分数。

当前按 metrics 动态展示，读取实际字段，明确显示 engine、valid_counts、complete_count，缺失分数不会显示成零。Streamlit AppTest 用可控 HTTP 返回值操作“RAG 评估→输入问题→开始评估”，断言 `0.75` 显示为 `0.750`，null 显示为“未评出”。这是 Streamlit 应用级交互验证；浏览器插件连接失败，未完成截图与浏览器控制台验证。

### 问题 21：依赖能 import 就算安装正确吗？

不算。环境中已安装包可能违反别的包声明的版本范围，某些路径暂时不触发错误而已。本次发现 Streamlit 要求 PyArrow<25，但环境中存在 25.0.1，因此补充了 demo 可选依赖及范围约束，并检查锁文件解析。

pyproject.toml 的主依赖与 requirements.txt 同步；uv.lock 决定 uv 安装的精确解析版本，pip 直接依赖列表不等于完整锁定。CLI 入口原先指向不存在的 med_rag 模块，现改为 main:main；包发现范围收窄，避免把模型、数据和虚拟环境作为源码包分发。依赖更新状态以审查报告为准。

### 问题 22：前端构建为什么也是项目完整性问题？

原构建命令把网页产物与文档、PPT 等混放 artifacts；更换构建工具或清理参数后可能误伤交付物。现在网页输出固定在 frontend/dist，幻灯片 HTML 输出 dist-slides；Windows 不再需要 rm 命令才能开始构建。

旧 PPTX 导出命令引用仓库不存在的 .codebuddy 工具，已经移除无效入口，原演示 PPT 文件完整保留。静态演示源代码和二进制 PPT 可能仍保留历史口径，展示前应以当前架构和本专题核对。构建成功证明资源打包和脚本执行，不代表内容事实已获医学审查，也不等于视觉布局验收。

### 问题 23：为什么没有直接证明“零错误”？

有限的测试只能覆盖特定输入、环境和故障条件。真实模型行为、外部服务、数据质量、接口权限、并发负载和临床适用性都有独立验证要求。一个回归全绿的技术演示，仍不能被称为任何情况下绝对正确的医疗系统。

本次明确区分源码编译、功能单元回归、SDK 故障注入、HTTP 契约、Streamlit AppTest、前端构建与真实端到端评测。报告同时写明未验证事项，避免用其中一层的成功替代另一层。面试中这种证据边界比“所有问题都已解决”的口头保证更可核实。

### 问题 24：如何向面试官讲述这次工程改进？

可以按“症状→根因→修复→验证→边界”展开。例如缓存案例：同一输入形式下出现剂量混淆；发现标点归一化在哈希前丢失语义；改为保留语义字符并加入上下文维度、使用 v2 命名空间；用小数点、斜杠、正负号、来源和历史差异的测试验证；最后说明模型/知识库版本失效还需要后续设计。

故障案例可说明：旧实现把数据库异常转换成空结果，子查询合并又可能隐藏 error；修复跨层错误传播并禁止 L2 缓存；测试在真实包装层注入 SDK 错误，并验证最终未调用 LLM。这是可指向代码和测试的个人工程工作，不能扩写成没有证据的生产事故恢复、业务收益或性能提升百分比。

### 问题 25：为什么测试套件通过，单独启动仍然可能崩溃？

测试进程会按测试文件和模块的顺序导入依赖。这个顺序可能提前初始化某个原生库，使真实入口的加载问题在测试中没有出现。本轮回归套件曾通过，但独立运行质量测试、降级测试和 API 的 `--help` 都出现 Windows `0xC0000005`，不能据此把启动命令也写成通过。

最小实验记录在审查目录的 `import_probes.json`：直接导入 FlagEmbedding 或 API 会崩溃，先导入 PyArrow 再导入同一模块则成功。清理 PATH 后仍可复现，说明“只是 Conda 路径冲突”不足以解释本次故障。当前在 Windows 的 src 包初始化阶段先加载 PyArrow，避开深层依赖链初始化；该措施不加载模型、不连接数据库。这里证明的是当前环境中导入顺序与故障的关系，没有通过原生调试器证明具体 DLL 内部的根因。

同时修复 `run_api_safe.ps1`：调用外部程序时参数之间不加数组逗号，并透传 Python 退出码。之前 PowerShell 会把 `'-X',` 作为文件名参数，且失败状态可能被掩盖。验收需要分别运行独立启动命令、原有测试和新回归，不能只在同一个已经加载好依赖的测试进程中检查。`--help` 通过只证明入口能解析，不代表模型、数据库和真实问答已经联通。

### 问题 26：没有训练好的意图分类器，能否用基础 BERT 顶上？

不能把基础 BERT 的随机分类头当成可用的 general/medical 分类器。模型能执行 forward、softmax 能输出概率，并不说明这个概率有任务意义。如果医疗问题被随机分到 general，可能绕开医学检索链路，造成错误路由。

当前优先寻找正式分类器目录，再找备份目录；没有分类权重时明确报错。训练入口 `scripts/train_intent.py` 仍可从基础 BERT 开始微调，训练与推理职责不同。回归覆盖“缺权重不能静默运行”；真实分类准确率、医疗漏分率及分布变化仍需专用测试集测量。面试中应解释训练数据、标签定义、混淆矩阵和错误代价，不能用“用了 BERT”代替质量证据。

### 问题 27：合并多份评测报告时，哪些细节会悄悄改变结论？

必须统一引擎、指标集合、有效值范围、去重规则及统计分母。旧 `merge_eval_chunks.py` 按“至少一项大于零”筛选裁判分块，导致真实全零样本被排除，而全局均值又把缺失值补成零，两种统计口径不一致。

当前只合并明确标记 ragas 引擎、四项评分均为有限且处于 [0,1] 的行；真实全零保留，布尔值、null、NaN、缺项及越界值排除并计数；全局和裁判分块使用同一批去重后的有效行。没有有效行的裁判分块均值为 null，打印 NA。指定文件不存在会失败，不静默生成一份残缺报告；CSV 的父目录也会自动创建。

完整样本统计仍可能产生选择偏差：如果困难题更容易超时，删除不完整行会高估质量。因此必须同时报告 `n_invalid_dropped`，保留原始分块用于排查和补评。不同裁判负责不同题块的均值差混合了题目难度与裁判口径，不能当成纯粹的裁判方差，也不能称为每题多裁判 ensemble。

## 三、后续验收任务与未实现能力

1. **真实中间件联调：** 在明确地址、集合和数据版本后验证 Milvus、Redis、MySQL 的正常与断连场景；记录集合行数、过滤表达式和返回样本。
2. **数据迁移：** 保留旧分块备份，验证 parent_id、chunk_type 和正文关联；代码防护不能代替存量数据修复及重新清洗。
3. **同口径质量评估：** 固定题集、答案生成模型、裁判、提示词和检索参数，记录每项有效数；修复后重新生成答案才能归因到新版本。
4. **FAQ 标定：** 覆盖否定、近邻实体、数值单位和不在库问题，统计错误直答率与覆盖率，选择明确的拒答规则。
5. **权限与隐私：** 当前 API 没有用户身份验证及会话所有权检查；session_id 本身不是授权机制。需要认证、访问控制、限流及敏感数据治理后才适合公网多用户场景。
6. **并发与生命周期：** 当前路由中仍有同步模型调用，共享数据库连接需要专门的并发设计与测试；健康页部分状态仅代表对象已初始化。
7. **多轮检索：** history 已参与缓存与生成，但检索仍以当前问题为主，没有完整的指代补全与查询改写。
8. **文档格式：** OCR、复杂表格、图片文字和通用章节结构恢复尚未实现；来源名称不代表授权或医学内容审查已经完成。

这些条目保留为真实后续工作；不会因为增加文档、通过 mock 测试或保留一份历史报告，就变成已实现功能。
