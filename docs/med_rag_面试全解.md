## 0. 三十秒电梯陈述（面试开场必背）

> 这是一个**医疗科普领域的 RAG 问答系统**。知识源是《默沙东诊疗手册（大众版）》，清洗后 2570 篇 Markdown，父子分块成 20816 个文本单元，用 BGE-M3 同时生成稠密向量和稀疏词权向量，存进 Milvus 做混合检索。
> 在线链路是：Redis 缓存 → **FAQ 快通道**（MySQL+BM25，softmax 归一化后阈值 0.85 判定，命中即返、零 LLM 调用）→ 未命中**降级**至 RAG 深通道（意图分类 → LLM 自动选四种检索策略之一 → Milvus 混合检索并**下推子块过滤** → Small-to-Big 回溯父块 → 用最佳命中子块作为证据做 BGE-reranker 精排、返回 Top-2 完整父块）→ 拼上下文 → 环境变量配置的 OpenAI 兼容模型生成带来源的答案。会话存 MySQL 支持多轮，最后用 Ragas 做四指标离线评估。可靠性上还做了**分层降级**：检索为空时不会让 LLM 凭空作答，而是安全拒答并引导就医，原则是「降级路径必须比主路径更安全，而不是更粗糙」。
> 我做这条链路的核心价值不在"调了几个模型"，而在**把"答案可溯源"这件事工程化**：每一条回答都带命中的原文块和相似度，医疗场景里这比"答得像不像"更重要。

## 2. 完整流程讲解

### 2.1 离线建库（Offline Indexing）—— 一次性的"喂知识"

```
《默沙东诊疗手册》原始数据 (data/raw)
   ↓ ① 抽取      scripts/extract_msd.py
   ↓ ② 加载      document_loader.py   多格式解析（含 OCR 兜底）
   ↓ ③ 清洗      data_cleaner.py      去导航/广告/版权/页码/重复行，抽取标题与来源元数据
   ↓ ④ 分块      chunk_splitter.py    父子双层分块（父 2000 / 子 400，overlap 60）
   ↓ ⑤ 向量化    embedding_provider.py  BGE-M3 一次前向 → dense(1024) + sparse(词权字典)
   ↓ ⑥ 入库      milvus_store.py      建集合/建双索引/分批 insert（batch 1000）
   ↓
Milvus: med_msd_consumer_chunk
```

**四个关键决策及其理由**（面试讲这里最有信息量）：

1. **为什么清洗要单独一步？** 手册 HTML 里混着导航链接、"本页面仅供…"版权声明、分页符。这些东西进向量库后会成为"高相似度噪声"——它们重复出现在每一页，IDF 极低但在 dense 空间里会形成一片高密度区域，把不相关 query 吸过去。清洗不是洁癖，是召回质量的前置条件。
2. **为什么用父子分块而不是固定大小分块？**
   - 块太小（400 字）：语义完整、检索精准，但 LLM 拿到的上下文残缺，答案会"只说一半"。
   - 块太大（2000 字）：上下文完整，但一个向量要编码 5 个不同主题，向量被"平均化"，检索精度下降。
   - 父子方案：**用小粒度去检索（精度），用大粒度去生成（完整）**。这是 RAG 里成本最低、收益最稳的一个工程技巧。
3. **为什么选 BGE-M3？** 见 §3.1，它一次前向同时出稠密 + 稀疏两种向量，省掉"再跑一个 BM25"的额外链路。
4. **GPU 上的工程细节**：BGE-M3 fp16 约 1.1GB 显存，你的 RTX 4060 Laptop 8GB 能塞下；`batch_size=64`（不是 128，128 会因显存碎片顶到 8G 上限而**空转降速十几倍**）；每批结束 `torch.cuda.empty_cache()`；`max_length=2048`（不是 8192，8192 纯浪费）。这几个数字是踩坑踩出来的，面试讲出来很加分。

### 2.2 在线问答（Online Pipeline）—— 每次提问都走一遍

代码入口：`main_api.py::_handle_query`（284-393 行）

```
用户提问
  ↓
【0】session_id：前端生成写入 URL 参数；未提供则后端 uuid4()
  ↓
【1】Redis 缓存查询   key = query:md5(规范化问题)   → 命中直接返回（最快路径）
  ↓ 未命中
【2】快通道：FAQ 二级检索（所有问题都先过这一关，不再做意图预判）
      Redis(faq:*) 一级 → 未命中 → MySQL + jieba BM25 二级
      → BM25 原始分（~7 量级）经 **softmax 归一化**到 (0,1]
      → 阈值 **0.85** 判定：命中则 intent='faq'，confidence 0.95，写回 Redis，直接返回
      → 未命中 → **降级**进入深通道
  ↓ 降级
【3】深通道：RAGSystem.generate()（rag_system.py:54-129）
     3.1 意图分类（**全链路唯一一次**，仅在深通道内执行）
         └─ general → 空上下文 + LLM 直答，不检索
     3.2 策略选择：LLM 从 direct / hyde / subquery / backtracking 四选一
     3.3 检索与合并（统一走 **Small-to-Big**）
         - BGE-M3 一次前向 → dense(1024) + sparse(词权)
         - Milvus 混合检索 + **子块过滤下推** → Top 16 子块
         - 按 parent_id 回溯父块并去重（16 子块 → 通常 3-5 个父块）
         - hyde → 先让 LLM 生成"假设答案"，用假设答案去检索
         - subquery → LLM 拆成 N 个子问题，各自走 Small-to-Big 后按父块 id 去重
     3.4 重排序：BGE-reranker CrossEncoder，对去重父块精排 → **Top 2**
     3.5 构建上下文：【知识来源1】...【知识来源2】... 拼接
     3.6 LLM 生成：system prompt（医疗助手人设 + 不编造 + 仅供参考）+ 最近 3 轮历史
  ↓
【4】写 MySQL conversations（双向：问 + 答）
  ↓
【5】写 Redis 缓存（type='rag'）
  ↓
返回 {answer, sources, confidence, intent, strategy, session_id, response_time, degraded, degraded_reason, degraded_level}
```

**为什么 FAQ 要从"意图分支"改成"第一通道"？**（改造动机，值得讲）

原设计是「意图分类 → general 走 FAQ / medical 直接进 RAG」。这个"医疗保护"是**用架构绕开缺陷**：因为 BM25 阈值失效，才不敢让医疗问题碰 FAQ。

真正的病根是**评分尺度没校准**——FAQ 表的 `question` 存的是**文章标题**，BM25 按标题做字面匹配时，"医生，我头痛"会被匹配到《声带息肉，结节，肉芽肿，乳头状瘤》，因为"医生"这个高频词撑起了分数，而阈值 0.5 对 ~7 量级的原始 BM25 分数形同虚设。

修法是**给 BM25 做 softmax 归一化**，把分数压到 (0,1]，阈值 0.85 才真正有区分力。归一化之后：

- 阈值生效了，不再需要"医疗保护"这种绕路设计 → FAQ 可以提升为第一通道
- 关键词守卫（`_question_relevant()`）这个 hack 也可以删掉 → 少一层特例逻辑
- 顺带消掉了意图分类跑两次的问题（原来 main_api 预判一次、rag_system 内部再算一次）

**这个 case 是项目里最值得讲的一个 bug fix**：它不是模型问题，是"评分尺度没校准"的典型工程问题——而且修好根因之后，可以反过来简化架构。这个思路比"打补丁"高一个层次。

### 2.3 评估闭环（Evaluation）

- 框架：Ragas 0.2.x，judge = LLM，embedding = 复用本地 BGE-M3（保证与检索阶段同分布，且不需要额外密钥）。代码 `rag_evaluator.py`。
- 两种模式（`scripts/evaluate_rag.py`）：
  - **实时管线模式**（默认）：读测试集 → 真跑一遍完整 RAG → 拿真实答案和上下文打分。最贴近线上。
  - **静态模式**（`--static`）：对已固定的 QA 对直接打分，不跑检索。
- 四指标：faithfulness（不杜撰）/ answer_relevancy（不跑题）/ context_precision（召回的片段都是有用的）/ context_recall（该召回的都召回了）。
- **注意**：`context_precision` / `context_recall` 需要 `ground_truth`；你的 `eval_report.json` 里 `has_ground_truth: false`，所以只跑出两项。CSV 里那两个 1.0 是静态模式下 ground_truth 由 contexts 构造导致的自证，见 §6.2 #1。

## 3. 技术深挖（逐项：是什么 → 为什么 → 追问 → 拓展）

### 3.1 BGE-M3：一个模型，三种检索能力

**是什么**：BGE-M3（M3 = Multi-Linguality, Multi-Functionality, Multi-Granularity），BAAI 2024 年发布的检索模型。

**三种输出**：

| 输出 | 形态 | 作用 | 本项目 |
|---|---|---|---|
| Dense | 1024 维稠密向量 | 语义相似，可处理同义/改写 | ✅ 用 |
| Sparse | `{token_id: weight}` 词权字典，类 BM25 | 精确词面命中，处理专有名词、药品名 | ✅ 用 |
| ColBERT / multi-vector | 每 token 一个向量，做细粒度 late interaction | 长文档精确匹配，代价大 | ❌ 关闭（`return_colbert_vecs=False`） |

**为什么它比"BERT 句向量"强？** 传统句向量（如 simcse）只在语义空间可比，遇到"布洛芬" vs "芬必得"这类**字面不同但语义近**可以，遇到"1 型糖尿病" vs "2 型糖尿病"这种**字面极近但语义相反**就废了。稀疏向量正好补上这一刀——它保证"1型/2型"这种关键区分词必须命中。

**为什么它比"两个模型拼"省？** 一次前向同时出两种向量，不用再维护 BM25 索引（虽然你 FAQ 那边还是手写了 BM25）。而且稀疏权重是**模型学出来的**，比统计式 BM25 更懂"哪个词该重"。

**追问**：
- Q：稀疏向量和 BM25 的区别？→ BM25 是统计式（TF-IDF + 长度归一化），权重来自语料统计；BGE-M3 的 lexical weights 是**模型预测**的，相当于"学习的稀疏表示"，会主动给语义关键词更高权重、给停用词 0 权重。
- Q：为什么不启用 ColBERT？→ 存储和计算成本高（每 token 一个向量，一个 400 字块要存 ~300 个向量），20816 块会膨胀几十倍；且你已经用 reranker 做了精排，收益重叠。
- Q：max_length 为什么 2048？→ 文本块最长约 1333 token，2048 留足余量；设 8192 会按最长批次分配显存，白白 OOM。

**拓展**：
- **Late Chunking**（2024）：先让长文本过一遍 Transformer 拿到全序列 token 向量，再分块做 pooling。好处是每个块的向量都带有全局上下文，解决"这块里的'它'指谁"的问题。Jina 有现成实现。
- **Matryoshka Embedding（套娃表示）**：训练时让向量的前 64/128/256 维也能单独用，线上可以按需要截断维度省存储。BGE-M3 官方支持。
-  multilingual 能力：M3 支持 100+ 语言，中英混排的医学术语（如 "CT"、"HbA1c"）是它的强项。

### 3.2 Milvus 混合检索：索引、度量与融合

**索引选择**：

| 字段 | 索引 | 参数 | 为什么 |
|---|---|---|---|
| dense_vector | IVF_FLAT | nlist=256, nprobe=16, metric=IP | 2 万条数据量级，IVF_FLAT 已经是精确检索 + 聚类剪枝，不需要 HNSW 的图结构；数据涨到百万级再换 HNSW 或 IVF_PQ |
| sparse_vector | SPARSE_INVERTED_INDEX | drop_ratio_build=0.2 / drop_ratio_search=0.2 | 倒排索引天然适配稀疏向量；drop_ratio 丢弃低权重词项，近似检索换速度 |

**为什么 metric 用 IP（内积）不用 L2？** BGE-M3 输出的向量是**归一化过的**，此时 `cosine = IP = 1 - L2²/2`，三者等价但 IP 计算最省（不用开方）。这是个常考点。

**融合方式：WeightedRanker(dense 1.0, sparse 0.7)**

Milvus 的 `WeightedRanker` 做的是**分数归一化后的加权求和**：先把每路结果的分数各自归一化到 [0,1]（解决 dense IP 分和 sparse 词权分不同量纲的问题），再按权重相加。**不是直接把原始分乘权重**——很多人答错这点。

**对比 RRF（Reciprocal Rank Fusion）**：

| | WeightedRanker | RRF |
|---|---|---|
| 用什么的 | 用**分数** | 只用**排名**（`Σ 1/(k+rank_i)`，k 常取 60） |
| 优点 | 保留相关性强度信息 | 完全不依赖分数尺度，鲁棒 |
| 缺点 | 两路分数分布差异大时，权重难调 | 丢掉了"第一名比第二名强多少"的信息 |

**面试话术**：*"我用的是 WeightedRanker，dense 1.0 / sparse 0.7。这不是网格搜索出来的理论最优，而是对齐 EduRag 的初值后在医疗语料上人工调的——偏向 dense 主导、sparse 补充。更严谨的做法是构造带标注的召回评测集，用 Recall@K / NDCG@K 做权重搜索，或者直接换 RRF 规避量纲问题。这是我知道的一个可优化点。"* —— 主动承认 + 给出方案，比硬吹权重好得多。

⚠️ 若被追问"A/B 测试数据呢？"——**诚实回答没做显著性检验**。硬编数据会被追问穿。

### 3.3 父子分块（Small-to-Big / Parent-Child Chunking）

**机制**：父块 2000 字保留完整逻辑，子块 400 字用于向量检索。子块通过 `parent_id` 指回父块，且**父块正文被冗余存进子块记录的 `parent_content` 字段**（避免二次查询）。代码见 `chunk_splitter.py:163-174`、`milvus_store.py:158-167`。

**为什么冗余存而不二次查？** 一次 Milvus 查询 ~10ms，但按 `parent_id` 回查是**串行依赖**（先拿到子块 id，才能查父块），在线链路里这一来一回直接翻倍延迟。冗余存父块正文（65535 字符上限）是典型的空间换时间。

**追问**：
- Q：overlap 60 是干嘛的？→ 防止一个完整的医学论点被切断在块边界。60 字符约为一个中文句子长度。
- Q：为什么不按段落/标题切？→ 医学手册的段落长度极度不均（有的 50 字，有的 2000 字），按字数 + 递归分隔符（"\n\n" → "\n" → "。" → "！" → "？" → "；" → "：" → "," → " " → 字符）是更稳的工程折中。
- Q：你的分隔符为什么把中文标点放在英文逗号前面？→ `RecursiveCharacterTextSplitter` 按列表顺序**依次尝试**，先用大粒度分隔符，切不开才降级。中文文本里句号是最自然的语义边界，优先级必须高于逗号/空格。

**拓展**：
- **语义分块（Semantic Chunking）**：按相邻句子的 embedding 相似度切分，相似度骤降处断开。比字数切分更贴合语义，但需要调阈值。
- **文档层级分块**：Markdown 天然有 `#/##/###`，按标题层级建树，检索时带上"祖先标题路径"作为上下文前缀（解决"这块属于哪篇文章的哪一节"）。
- **命题级分块（Proposition Indexing）**：把文本拆成原子事实句，检索精度最高，但需要 LLM 离线处理，成本高。

### 3.4 BGE-reranker：CrossEncoder 精排

**核心区别：双塔 vs 单塔**

| | 双塔（Bi-Encoder，BGE-M3 检索） | 单塔（CrossEncoder，BGE-reranker 重排） |
|---|---|---|
| 输入 | query 和 doc **各自独立**编码 | query 和 doc **拼接**后一起编码 |
| 交互 | 只在最后算一次余弦 | 全程 self-attention 交互，每对 token 都能看到对方 |
| 精度 | 中 | 高 |
| 速度 | 毫秒级，可离线预编码文档 | 慢，**必须在线算**，无法预编码 |
| 适用 | 全库召回（2 万条） | 只对去重后的父块精排（通常 3-5 条） |

**这就是两阶段检索（Retrieve & Rerank）存在的全部理由**：用便宜的召回从 2 万缩到 Top-16 子块，回溯去重成 3-5 个父块；重排时对每个父块的最佳命中子块证据打分，最终返回 Top-2 完整父块。**如果只有 reranker 没有召回，20816 个块每个都要跑一次 CrossEncoder，成本与延迟都会过高。**

**代码细节**：`FlagReranker.compute_score(pairs)`，单 pair 返回标量、多 pair 返回 list，代码里做了兼容（`reranker.py:80-83`）。这个 API 不一致是 FlagEmbedding 的历史坑，踩过才知道。

**拓展**：
- **精排后还要不要 LLM 重排（RankGPT / listwise）？** 三轮重排成本高，一般只在 Top 5 以内、且业务对排序极敏感时用。
- **重排分数做阈值截断**：低于某分数的文档直接丢弃，宁可说"知识库里没有"，也别把不相关内容塞给 LLM 逼它编。医疗场景尤其重要。

### 3.5 BERT 意图分类：为什么不用 LLM 分类

**为什么用一个小 BERT 而不是让 LLM 判断"这是不是医疗问题"？**

| | BERT 微调 | LLM zero-shot |
|---|---|---|
| 延迟 | ~10ms（本地 GPU） | ~500ms-1s（网络 + 生成） |
| 成本 | 0（本地推理） | 每次问答多一次 API 调用 |
| 位置 | 在缓存之后、FAQ 之前，**每次请求都跑** | 会显著拖慢主链路 |
| 稳定性 | 输出确定 | 输出有随机性，且要解析文本 |

**这个决策的关键是"它在关键路径上"**。策略选择用 LLM 是因为它每次问答只跑一次、且需要推理能力；意图分类每个请求都要跑、且是简单二分类，用小模型是必然选择。这个对比本身就是一道很好的架构题。

**训练配置**：`bert-base-chinese` + `BertForSequenceClassification(num_labels=2)`，3 epoch，batch 8，warmup 500，weight_decay 0.01，早停 patience=2，max_len 128。

### 3.6 四种检索策略（Query Augmentation）

| 策略 | 机制 | 适用场景 | 代价 |
|---|---|---|---|
| direct | 原 query 直接检索 | 意图明确的事实型问题："高血压正常范围是多少" | 0 |
| hyde | 让 LLM 先生成一段**假设答案**，用假设答案的向量去检索 | query 抽象、需要推理："糖尿病不控制会怎样" | +1 次 LLM |
| subquery | LLM 拆成 N 个子问题，各自检索后合并去重 | 多实体/多侧面："比较 1 型和 2 型糖尿病的病因与治疗" | +1 次 LLM + N 次检索 |
| backtracking | LLM 把具体问题**抽象成更基础**的问题再检索 | query 太具体导致字面匹配不到："我家族有糖尿病史，最近口渴多尿，是不是得了糖尿病" | +1 次 LLM |

**HyDE 为什么可能有效？** query（短、口语、疑问句式）和 doc（长、书面、陈述句式）在向量空间里存在表达差异。HyDE 先生成一段假设答案，使检索文本形式更接近文档，某些问题上可能改善召回；但假设答案中的幻觉词也可能把检索带偏，收益必须用召回评测集验证。

**追问**：
- Q：subquery 合并时怎么去重排序？→ 每个子查询各自走一遍 Small-to-Big 得到父块，再按**父块 id** 去重（同一父块保留最高分），按分数降序交给精排（`rag_system.py:186-197`）。注意这里去重的是**父块 id 而非子块 id**——因为多个子查询可能命中同一父块的不同子块。
- Q：策略选错了会怎样？→ 不会崩。所有策略最终都落到 `Retrieval.search`，且 LLM 没返回合法策略时 `_normalize_strategy` 会兜底 direct。这是**优雅降级**的设计。
- Q：四种策略有做 A/B 对比吗？→ `[待确认]` 仓库里没有对比数据。**这是面试会被追问的点**，诚实回答 + 给出评测方案。

**拓展**：Query Rewriting（用多轮历史改写当前 query，解决"它有什么副作用"的指代问题）——**你的项目目前没有做这一步，是个明确的可改进点**，见 §6.2 #3。

### 3.7 缓存与稳定键（一个真实的工程坑）

`cache_manager.py:39-46` 里有个细节值得单独讲：

> 不要用 Python 内置 `hash()` 做缓存键。Python 对 str 的 `hash()` 默认启用 **PYTHONHASHSEED 随机化**，同一个字符串在不同进程（每次重启服务）里会算出不同的值，导致 Redis 缓存**永远无法跨重启命中**。

改成 `hashlib.md5(规范化文本)` 后就稳定了。规范化会剔除所有空格和中英文标点（`[^\w\u4e00-\u9fff]`），让"感冒吃什么药？"和" 感冒吃什么药 "命中同一条缓存。

**另一个坑**：`redis-py` 5.3.x 在 Redis 不可达时，`CLIENT SETINFO` 会触发 `on_connect → send_command → 重连 → on_connect` 的**无限递归**，最终抛 `RecursionError`（不是 `ConnectionError`，原来的 except 抓不到）。解法是把 `lib_name=""` 和 `lib_version=""` 传进连接池，跳过该命令（`cache_manager.py:80-96`）。

### 3.8 Ragas 四指标（要能讲清每个指标怎么算）

| 指标 | 算什么 | 大致算法 | 需要 ground_truth |
|---|---|---|---|
| faithfulness 忠实度 | 答案有没有超出给定上下文 | LLM 把答案拆成若干 claim，逐条判断是否能在 contexts 中找到支撑，`支持数 / 总 claim 数` | ❌ |
| answer_relevancy 答案相关性 | 答案切不切题 | 用答案**反向生成**若干问题，与原始问题算 embedding 相似度取均值 | ❌ |
| context_precision 上下文精确度 | 召回的片段里有多少是真的有用的 | 逐条判断 context 是否与 ground_truth 相关，做排序加权（有用的排前面得分更高） | ✅ |
| context_recall 上下文召回率 | ground_truth 里的信息被上下文覆盖了多少 | 把 ground_truth 拆成 claim，看多少能在 contexts 中找到 | ✅ |

**重要理解**：faithfulness 低 = **生成端幻觉**；context_recall 低 = **检索端漏召**。这两个指标能帮你定位问题在哪一段，这是 Ragas 最大的价值——不是给你一个总分，是给你一个**归因坐标**。

**追问**：Ragas 用 LLM 当裁判，裁判本身不准怎么办？→ 答：① 用跨厂商多模型集成当 judge（如本次 deepseek/glm/minimax/hy 共 6 个模型并行打分取均值），稀释单模型偏好与校准方差；② 抽样人工复核校准；③ 关注**相对变化**而非绝对值（A/B 两个版本谁高谁低比"绝对是 0.88"更可靠）；④ embedding 复用检索同款 BGE-M3，保证评估与线上同分布。

### 3.9 Windows + GPU 上的工程坑（面试讲出来极加分）

| 坑 | 现象 | 解法 |
|---|---|---|
| Intel OpenMP 冲突 | torch/FlagEmbedding 与 numpy MKL 重复加载 `libiomp5md.dll`，进程直接 `0xC0000005` 崩溃，**没有 Python 堆栈** | 在**任何** torch/numpy 导入**之前** `os.environ.setdefault("KMP_DUPLICATE_LIB_OK", "TRUE")`（`settings.py:6`，必须在文件最顶部） |
| uv venv 缺 VC++ 运行时 | 进程崩溃 | 自包含 8 个 DLL 到 venv |
| GPU 显存碎片 | batch 128 持续跑会顶到 8G 上限，分配器空转，**每批骤降十几倍** | batch 降到 64 + 每批后 `torch.cuda.empty_cache()`（`embedding_provider.py:228-233`） |
| max_length 过大 | 8192 按最长批次预分配显存 → OOM | 降到 2048（最长文本才 1333 token） |
| redis-py 递归 | 见 §3.7 | `lib_name=""` |
| 上次建库中断 | 有集合但无索引，Milvus 拒绝 load（`code=700 index not found`） | `create_or_load_collection` 里幂等调 `_create_indexes`（`milvus_store.py:106-109`） |

### 3.10 分层降级策略（L0 / L1 / L2）—— 最值得主动讲的设计题

**是什么**：检索不一定每次都有结果。项目把"检索失败"从一句 if 兜底，改成三层显式策略。

一句话原则（**这句是全场最值钱的一句**）：

> **降级路径必须比主路径更安全，而不是更粗糙。**

| 层级 | 触发条件 | 行为 | 输出粒度 | 风险 |
|---|---|---|---|---|
| **L0** | 正常 | 严格 Small-to-Big：`chunk_type` 过滤下推只召回子块；命中却找不到父块的 orphan 记 ERROR 并剔除 | 400 字子块 → 2000 字父块 | 基线 |
| **L1** | 子块召回为空 | **同粒度降级**：放开子块过滤重查；命中父块后用 `_split_parent_in_memory()` **现场切成 400 字子块**再返回，且有候选上限防膨胀 | **仍是 400 字子块** | 不上升 |
| **L2** | L1 仍为空 / 基础设施故障 | **安全拒答**：返回固定话术，**不调用 LLM** | 无上下文 | 最低 |

**为什么这么设计（三个追问，提前准备好）**

1. **"检索不到的时候，直接把 2000 字父块返回给 LLM 不就行了？"**
   → 这是**质量下降伪装成降级**。父块会稀释 LLM 注意力（Top-2 里塞进大量无关段落）、token 翻倍，
   更糟的是它**掩盖了数据问题**——这块文本为什么没被切成子块？是不是切分逻辑有 bug？
   静默返回父块 = 用"能出答案"掩盖"链路已经不正常"。
   **所以这条路径没有开关，永久禁止**（`settings.py` 里有注释明确说明）。

2. **"L1 为什么要现场切成子块，直接用父块不是更简单？"**
   → 因为 L1 的语义是**换检索入口**（从子块层换到父块层），不是**降输出质量**。
   现场切分用与离线建库**共享的 `SEPARATORS` 常量**，保证线上线下切分同构，
   输出粒度和 L0 完全一致，下游的 Top-N 截断、精排、拼上下文的行为都不需要为降级分支写特例。

3. **"L2 为什么不调用 LLM？用户问了总得给点东西吧？"**
   → 医疗场景里，检索不到依据时让 LLM 用参数知识硬答，是**整条链路上风险最高的行为**：
   它会编，而且语气权威，用户无法分辨。宁可拒答并引导就医。
   对应配置 `ALLOW_LLM_WHEN_NO_CONTEXT = False`，**默认关闭且不建议打开**。

**可观测性（这段能体现工程成熟度）**

- `RetrievalResult` 是 Sequence 代理：既能当 list 用（向后兼容老代码），又带 `.documents` / `.watermark` / `.reason` / `.failure` 四个字段，
  降级水位沿链路传播，不需要在每层重新判断。
- **多路子查询合并时取最差水位**——不允许"一路 L2、一路 L0"被平均成"看起来正常"（木桶效应）。
- `/health` 暴露降级计数器，`/query` 响应带 `degraded` / `degraded_reason` / `degraded_level` 三个字段，前端可以据此提示。
- **区分"召回为空"和"基础设施故障"**：都是 L2，但**故障导致的降级结果不写 Redis 缓存**
  ——否则故障期间的空结果会被缓存污染后续请求，故障恢复后还要等 TTL 过期。

**踩过的坑**（讲出来更真）：

- `reranker.rerank()` 内部会 `documents.sort()` 原地排序，把 `RetrievalResult` 包装对象直接传进去会崩
  → 主链路统一传 `.documents`（诊断脚本 `test_query_pipeline.py` 也同步修了）。
- L1 早期没有候选上限，一次能返回 14 条 / 5520 字，比 L0 还重 → 补上限。
- 错误路径里取属性会二次抛错，把真实的检索异常吞掉 → 日志改用 `getattr` 防御。

**验证方式**：`python scripts/test_degrade_policy.py`（9 项 mock 场景：L0 正常 / L0 orphan / L1 / L2 空 / L2 故障 / L1 禁用 / 兼容性 / 指标计数 / 拒答不调 LLM）。

## 4. 拓展：从"能跑的 Demo"到"能上线的系统"

按优先级排序，每一条都可以变成面试里的"如果让你继续做，你会怎么做"。

### 4.1 检索质量（收益最大）

1. **构造召回评测集**：从 2570 篇里人工/LLM 标注 200-300 条 (query, 相关 chunk_ids)，做 Recall@8 / MRR / NDCG@4。**没有这个，你所有关于"检索准不准"的说法都是空谈。**
2. **权重搜索 / 换 RRF**：见 §3.2。
3. **Query Rewriting**：用多轮历史改写当前 query（"饮食注意" → "1 型糖尿病患者的饮食注意事项"）。**这是多轮 RAG 的标准做法，也直接解决你 §6.2 #2 的缓存冲突问题。**
4. **多路召回 + RRF 融合**：BM25（真·语料级） + dense + sparse 三路。
5. **CRAG / Self-RAG**：让模型判断检索结果够不够（relevance token），不够就触发 web 搜索或改写重检索。医疗场景可以退化为"检索分数低于阈值 → 明确回答'知识库未覆盖'"，比硬编答案安全得多。
6. **查询扩展**：医学术语同义词表（"偏头疼"="偏头痛"="血管性头痛"），或者用 LLM 生成同义 query 做多路。

### 4.2 生成质量

7. **引用标注（Citation）**：要求 LLM 在答案里标注 `[1][2]` 对应到具体 chunk，前端可点击跳转。你现在只是把 sources 贴在旁边，**没有做答案内引用对齐**——这在医疗可解释性上是硬伤。
8. **结构化输出**：用 JSON schema / function calling 强制输出 `{症状, 诱因, 治疗, 来源}`，前端渲染更稳定（你 PPT P16 的 demo 已经是这个结构，但代码里是纯文本 prompt，靠模型自觉）。
9. **拒答与免责**：检索为空或 rerank 分数过低时，走固定兜底话术，不要让 LLM 自由发挥。

### 4.3 工程化

10. **异步化**：现在是同步链路，intent(BERT) + strategy(LLM) + retrieve + rerank + generate 全串行。可以并行的是：BERT 意图分类与 Redis/FAQ 查询（无数据依赖）。
11. **流式输出（SSE）**：`llm_generator.py` 已经有 `generate_stream`，但 API 层没暴露。医疗长答案的体验差别很大。
12. **组件复用**：`RAGSystem` 已经支持外部注入组件（`rag_system.py:33-52`），避免 FastAPI 每次请求重新加载大模型——**这点做得对，可以讲**。
13. **可观测**：每次问答记录 intent / strategy / 检索分数分布 / rerank 分数 / 各阶段耗时 / token 消耗，落表后做看板。这才是 PPT P15 说的"量化看板"的真正形态。
14. **知识更新与缓存失效**：现在 Redis TTL 固定 1 小时。知识库重建后应该有主动 purge 机制（按 collection 版本号做缓存前缀）。

### 4.4 领域深化（医疗）

15. **GraphRAG**：从手册里抽实体（疾病/症状/药品/检查）和关系（治疗/禁忌/并发症）建知识图谱，做"疾病-症状-用药"的多跳查询。这是当前 RAG 最热门的方向之一。
16. **结构化知识融合**：药品说明书里的剂量、禁忌是强结构化数据，用 Text-to-SQL 或单独的结构化检索比向量检索准得多——**这正好对应你 Prompt 文档里"确定性代码能稳定解决的，不交给 Agent 决策"**。
17. **合规与安全**：PII 检测、问诊意图识别（区分"科普咨询"和"我要你给我开药"）、强制免责声明、以及最重要的——**明确的转人工/就医建议触发规则**（红旗症状如胸痛、呼吸困难必须引导就医）。这是医疗 AI 的底线。

## 5. 面试攻防：高频问题 + 标准答案

> 用法：先自己答一遍再看答案。标 🔴 的是**一问就穿的高危题**，必须准备好。

### A 类 · 项目定位与业务

**Q1. 为什么做这个项目？解决什么问题？**
> 三层：① 通用大模型在医疗领域会"一本正经地胡说"，医学错误后果严重；② 权威医学科普分散在各平台，没有统一可信入口；③ 每次都走完整 RAG 成本高、速度慢，需要分层降本。
> 项目定位是**科普问答**，不是诊断——这个边界一定要说清楚，医疗 AI 面试里这是红线意识。

**Q2. 用户是谁？**
> 患者/家属（查症状、看科普）、医学生（快速检索权威资料）、大众（日常健康疑问）。**注意**：不要说"给医生做临床决策支持"——你的知识源是大众版科普手册，撑不起临床决策，说了会被追问穿。

**Q3. 为什么不用纯 LLM？为什么 RAG 是必要的？**
> ① 知识时效性/权威性：LLM 参数里的医学知识不可控、不可溯源；② 幻觉：医疗场景零容忍；③ 成本：把 2570 篇手册全塞进 prompt 不现实；④ 可解释：RAG 天然带引用。
> 加分：*"但我也不认为所有问题都要走 RAG——我用 BERT 把通用闲聊分流出去直答，就是为了不做无谓的检索。RAG 是手段不是目的。"*

**Q4. 🔴 这个项目和 Dify 上搭一个知识库工作流有什么区别？**
> 别答"我用了 LangGraph 所以替代不了"（你也没用 LangGraph）。真正难被低代码替代的点：
> ① **父子分块 + 父块正文冗余入库**的 schema 设计，Dify 的固定分块做不到；
> ② **双通道路由 + BM25 softmax 归一化**这套从业务 badcase 反推出来的设计（"头痛"被误匹配到"声带息肉"，根因是评分尺度没校准，修好后反过来简化架构）；
> ③ **混合检索的权重与索引调参**（IVF_FLAT nlist/nprobe、drop_ratio）；
> ④ **缓存稳定键、Redis 递归崩溃、显存碎片**这些工程问题只有在自己写代码时才会遇到。
> 诚实补充：*"如果只是一个 200 篇文档的内部 FAQ，Dify 确实够用，我不会硬上这套架构。这个项目的价值密度在于它把 RAG 每个环节都拆开自己实现了一遍。"*

### B 类 · RAG 核心技术

**Q5. 讲一遍完整的检索链路。**
> 见 §2.2。要能说出具体数字：BGE-M3 出 **1024 维 dense + sparse** → Milvus 混合检索（dense 1.0 / sparse 0.7，nprobe=16）**并下推子块过滤** → Top-16 子块 → 回溯去重成父块 → 以最佳命中子块为证据做 BGE-reranker 精排 → 返回 **Top-2 完整父块**。
> 加分：补一句“按现存 `docs.json` 的 `parent_id` 统计，逻辑父块 3936、逻辑子块 16880；旧产物的顶层 `chunk_type` 有标注缺陷，因此重新入库前应重生成，并用诊断脚本验证 live collection。”

**Q6. 🔴 为什么用 BGE-M3 不直接用 OpenAI 的 embedding 或者 m3e？**
> ① **一次前向出 dense + sparse**，省掉单独维护 BM25 索引；② 中文医学语义表现好且支持多语言混排（CT、HbA1c 这类术语）；③ **本地部署**，20816 块 × 1024 维的向量化如果调 API，成本高且慢；④ 支持 8192 长度（我用 2048）。
> 对比 m3e：m3e 只有 dense，需要额外配 BM25 才能做混合检索。

**Q7. dense 和 sparse 各解决什么问题？能只用一个吗？**
> 见 §3.1。核心例子："1 型糖尿病" vs "2 型糖尿病" 字面极近语义相反 → 靠 sparse 区分；"偏头疼" vs "偏头痛" 字面不同语义相同 → 靠 dense。**两个是正交能力，缺一个就有一类 query 会挂。**

**Q8. 🔴 为什么要 rerank？直接用向量检索的 Top-2 不行吗？**
> 见 §3.4 双塔 vs 单塔。核心：向量检索是**无交互**的（query 和 doc 各编各的），精度有上限；CrossEncoder 有**全交互**，精度高但必须在线算。两阶段是精度与成本的唯一解。
> 注意区分：召回阶段算的是**子块**分（400 字，语义聚焦），精排阶段算的是**父块**分（2000 字，上下文完整）。这两个分数不是同一批文档的分数，Small-to-Big 中间已经换过一次粒度了。

**Q9. 混合检索的 dense 1.0 / sparse 0.7 是怎么定的？**
> 🔴 高危题。诚实答：*"这是对齐 EduRag 的初值后在医疗语料上人工调的，dense 主导、sparse 补充，没有做系统的网格搜索。更严谨的做法是构造带标注的召回评测集，用 Recall@K / NDCG@K 搜参，或者直接换 RRF 规避量纲问题。这是我知道的可优化点。"*
> **千万不要编"我们做了大量实验得出最优"** —— 追问一句"实验集多大、指标是什么、有没有做显著性检验"就穿了。

**Q10. 分块怎么做的？为什么是 400 / 2000？**
> 见 §3.3。要讲出"小粒度检索保精度、大粒度生成保完整"的 trade-off。

**Q11. 四种检索策略怎么选的？有对比数据吗？**
> 🔴 高危题。答机制（见 §3.6）+ 诚实说：*"目前是 LLM 按 prompt 规则选择，还没有做四种策略在同一评测集上的 A/B 对比。如果要做，我会固定其他变量，在同一个 200 条评测集上分别强制跑四种策略，比较 Recall@8 和最终 faithfulness。"*

**Q12. 🟢 加分题：检索不到相关内容怎么办？**
> 这题已经从"待改进"变成**可以主动讲的设计题**，完整方案见 §3.10。
>
> **先亮原则**：*"我的原则是——降级路径必须比主路径更安全，而不是更粗糙。"*（这句话是全场最值钱的）
>
> **再讲三层**：
> - **L0** 严格 Small-to-Big，过滤下推只召回子块，orphan 父块记 ERROR 剔除；
> - **L1** 子块召回为空时**放开过滤重查，命中父块就在内存里切成 400 字子块再返回**——粒度不退化，只是换了检索入口；
> - **L2** 仍然为空或基础设施故障时**安全拒答，不调用 LLM**。
>
> **然后讲两个反直觉的取舍**：
> - *"L1 我**没有**做成'直接返回 2000 字父块'——那是拿质量下降伪装成降级：既稀释注意力、翻倍 token，又掩盖了'这块为什么没被切出子块'的数据问题。这条路径**没有开关，永久禁止**。"*
> - *"L2 也**没有**做成'让 LLM 凭知识兜底'——医疗场景里无依据硬答是整条链路风险最高的行为，它会编而且语气权威，用户分不清。宁可拒答引导就医。"*
>
> **最后讲可观测**：降级水位用 `RetrievalResult` 沿链路传播，多路合并取**最差水位**，`/health` 有计数器，响应里带 `degraded` 三个字段；并且**故障导致的降级不写缓存**，避免空结果污染故障恢复后的请求。
>
> 一句话版本：**"医疗场景'我不知道'比'我编一个'有价值一万倍，所以我让系统敢说不知道。"**

**Q13. 知识库更新了怎么办？**
> 现状：Redis TTL 1 小时被动过期，Milvus 集合没有版本字段。
> 改进：collection 加版本号或时间戳（`timestamp` 字段已有），缓存 key 带上知识库版本前缀，重建后主动切换前缀而非 flushdb（避免缓存雪崩）。可以做**增量入库 + 双集合灰度切换**（蓝绿），重建期间老集合继续服务。

**Q15. 🔴 Ragas 评估结果是多少？样本多大？**

> 测试集是 `eval_set_210.json`（带 `_source` 溯源字段）、答案缓存在 `eval_answers_210_grounded_v3_ar.json`。

> ground_truth **必须独立于检索行为**产生。我的做法是从 `data/clean_md` 随机抽 106 篇

**Q15.1 🟢 加分题："服用退烧药后多久可以重复用药"为什么两项都是 0.0？**
> **先说结论：不是检索失败，也不是降级拒答。实跑验证过，降级标记是 False，
> 命中了 2 条上下文（「药物相互作用」1987 字、「成年人发热」1229 字），检索是对的。**
>
> 真正的原因在知识库原文里。打开「成年人发热」这段：
> > 最有效和最广泛使用的退热药为对乙酰氨基酚和非甾体抗炎药 (NSAID)，
> > 如阿司匹林、布洛芬和萘普生。**这些药物需根据容器标签上的说明服用。**
>
> **知识库里根本没有"间隔 4–6 小时"这个数字**，原文只说"按标签说明服用"。
> 而系统的回答是：
> > ……**没有明确的时间间隔说明**。但以下信息可供参考：……重复使用间隔时间
> > **可能为 4 至 6 小时**……
>
> 于是 faithfulness=0 —— **Ragas 判得对**，那个"4 至 6 小时"是 LLM 的参数知识，
> 上下文里没有。
>
> **这件事暴露了三个不同层面的问题，我逐个讲：**
>
> ① **系统侧（最危险，也最值得讲）**：system prompt 第 3 条原来写的是
> 「如果信息不足，明确说明」。模型**照做了**——说了"没有明确的时间间隔说明"。
> 但这条约束**没说"然后停下"**，于是模型为了显得有用，紧接着补了一句参数知识。
> 这正是医疗 RAG 最坏的失败模式：**输出既含诚实的免责声明，又含无据的具体数值**。
> 它的危害大于直接编造——因为它看起来"已经核实过了"，而用户只会记住那个数字。
> 修法是把软约束改成硬约束：明确说明知识库未提供后，**不得**补充任何数值、
> 剂量、时间间隔、药名或诊疗建议。
>
> ② **评估侧**：ground_truth 写的"间隔 4～6 小时"知识库根本不支持，
> **这道题本身出得不合理**——测的不是系统能力，而是"LLM 是否碰巧知道答案"。
> 这正是手写测试集的通病，也反过来证明了测试集必须由源文档生成。
>
> ③ **指标侧**：answer_relevancy=0 偏严。该指标的做法是"从答案反向生成问题，
> 再与原始问题算语义相似度"，中文反向生成的措辞漂移比英文大，长答案下容易失真。
> 所以我看这个指标时会看**分布**而不是单点。
>
> **一句话收尾**：*"这个 badcase 我查完之后，反而更确信评估体系是有用的——
> 它精准地抓出了一个我自己没意识到的 prompt 缺陷。"*

**Q16. 你的 confidence 字段到底是什么的置信度？**
> 🔴 陷阱题。代码里 `confidence` 来自 `intent_classifier.predict()` 的 **softmax 概率**，是**意图分类的置信度，不是答案质量的置信度**（FAQ 分支还被硬编码成 0.95）。这是个命名误导。
> 正确做法：如果要表达答案可信度，应该用 rerank 分数 + faithfulness 在线估计，或者干脆改名为 `intent_confidence`。**主动指出自己代码的问题，比等面试官指出来强。**

**Q17. 🟢 加分题：父子分块怎么保证"只检索子块"？父块也在库里吧？**
> 这题原来是最狠的穿帮题，**现在可以主动讲，是个加分项**。
>
> **先讲数据边界**：现存 `docs.json` 共 20816 条；按 `parent_id` 统计为逻辑子块 16880、逻辑父块 3936。顶层 `chunk_type` 是修复前错误产物；本次 Milvus 未运行，不能据此断言当前线上 collection 的实体与 schema。
>
> **再讲我踩的坑**：最初子块过滤是在应用层做的——Milvus 先召回 Top-16（父子混合），再在 Python 里挑 `parent_id` 非空的子块。这有两个问题：
> 1. **槽位浪费**：2026-08-29 的历史诊断记录中，某次 Top-16 有 4 个父块、槽位浪费率 25%；这是当时样本，不应说成当前线上长期统计。
> 2. **静默失效**：原代码有条降级分支"挑不出子块就返回父块"，意味着最坏情况 Small-to-Big 完全没生效，而系统不报任何错。
>
> **然后讲修法**：把过滤**下推到 Milvus**。这里有个关键点——**Milvus 只能对顶层标量字段下推 `expr` 过滤，`metadata` JSON 内部的 key 是用不了的**。所以我给 schema 加了顶层 `chunk_type` 字段，检索时直接 `chunk_type == 'child'`。
>
> **兼容旧 schema**：没有 `chunk_type` 字段时用 `parent_id != ""` 过滤逻辑子块。若重建为带显式字段的新 schema，必须先重新生成当前顶层 `chunk_type` 错误的分块 JSON。
>
> **最后讲取舍**：我把那条静默降级分支**删了**，改成记录 ERROR。理由是在医疗场景里，静默返回 2000 字大块既稀释 LLM 注意力、翻倍 token，又掩盖数据问题——失败应该显式暴露。
>
> 一句话版本：**“代码已把子块过滤下推，并兼容旧 schema；历史诊断曾出现 Top-16 中 4 个父块，但当前 collection 仍需启动 Milvus 后复核。”**

**Q18. 多轮对话和 Redis 缓存会不会冲突？**
> 🔴 会。`query_cache_key` 只用 question 算 md5，**不带 session_id，也不带 history**。`/chat` 接口 `use_cache` 默认 True，所以"A 用户问'1型糖尿病'→ 追问'饮食注意'"时，如果"饮食注意"这个字符串之前被别人问过，会直接命中旧缓存返回通用答案，**多轮上下文完全失效**。
> 解法：多轮场景先做 **Query Rewriting**（把历史压缩进改写后的 query），再对改写后的 query 做缓存；或者 `/chat` 路径直接禁用缓存、只对 `/query` 单轮缓存。

**Q19. 意图分类为什么算了两次？**
> 🟢 **已修复**。原实现 `main_api.py` 先算一次 `pre_intent` 决定走不走 FAQ，`rag_core.generate()` 内部又算了一次。
> 修法不是"把 pre_intent 传参复用"，而是**从根上消除这个预判**——FAQ 提升为第一通道后不再需要意图来决定路由，意图分类只剩深通道内的一次调用。
> **讲法**：*"这个问题我没用传参复用去打补丁，而是重构了路由：FAQ 从意图的一个分支变成独立的第一通道，意图预判这个环节本身就不存在了，重复计算自然消失。"* —— 从"打补丁"升级到"消除根因"，层次更高。

**Q20. 会话保留 5 轮，但 Prompt 只注入最近 3 轮，为什么不一致？**
> `conversation_store.MAX_HISTORY_TURNS = 5`，`llm_generator.py:195` 用 `history[-3:]`。
> 可以解释为"存储冗余、注入截断"（存 5 轮是为了前端展示，用 3 轮是成本控制），但更好的是**把注入轮数做成配置项**并说明依据（token 预算）。直接答"随手写的"不行。

**Q21. `expr = f"source == '{source}'"` 有没有注入风险？**
> 有。`source_filter` 直接字符串拼接进 Milvus 过滤表达式。当前 source 来自内部前端，风险可控；但如果开放给外部，需要用参数化过滤或白名单校验。**能主动提到这个说明你有安全意识。**

**Q22. 服务是同步的，并发上来会怎样？**
> FastAPI 的 `def`（非 `async def`）路由会跑在**线程池**里，默认 40 线程。BERT 推理和 reranker 是 GPU 串行瓶颈，高并发会排队。改进：① 改成 `async def` + `run_in_threadpool`；② GPU 侧做 batch 聚合（攒批推理）；③ 缓存前置挡掉大部分请求。

**Q23. 🟢 加分题：你删掉过一条降级逻辑，为什么？**
> **先说事实**：Small-to-Big 里原本有一条"挑不出子块就直接返回 2000 字父块"的降级分支，我把它**删了**，改成记录 ERROR 并剔除。
>
> **再说判断依据**（这是面试官真正想听的）：降级的目的应该是**在主路径不可用时维持服务质量**，而这条分支做的是**牺牲质量换取覆盖率**——
> ① 2000 字父块塞进 Top-2 上下文，稀释注意力；② token 翻倍；③ 最关键的是它**静默掩盖了数据问题**——这块文本为什么没切出子块？是不是切分逻辑有 bug、是不是这批文档没走离线流水线？
> 一个"总能出答案"的系统，比一个"偶尔明确说不知道"的系统更难维护，因为你失去了发现问题的信号。
>
> **然后说替代方案**：我不是把它换成"报错"，而是换成**同粒度降级（L1）**——放开过滤重查，命中父块后现场切成 400 字子块，输出粒度和正常路径完全一致，下游不需要为降级分支写任何特例。
>
> 一句话版本：**"我删的不是降级能力，是那条用质量换覆盖率的降级路径；真正的降级我保留了，而且做得更严。"**

**Q24. 🟢 加分题：检索失败时，是"降级出答案"还是"失败显式暴露"？**
> **先破题**：*"我认为这是个伪二选一——真正的问题不是'降级还是暴露'，而是'降级到什么程度'。所以我的判断标准是：降级路径必须比主路径更安全，而不是更粗糙。"*
>
> **再给分层决策**：
> - **可以降级**的维度：换检索入口（子块层 → 父块层）、换模型（reranker 不可用则按原序返回）、换数据源（缓存 → 数据库 → 检索）。这些不影响输出质量，只影响实现路径。
> - **不可以降级**的维度：输出粒度（400 字 → 2000 字）、是否有依据（有上下文 → 无上下文让 LLM 硬答）。这些直接决定答案可信度。
> - **必须显式暴露**的：数据异常（orphan 父块）、基础设施故障。这类要在日志和 `/health` 里能看见，否则线上出问题你永远不知道。
>
> **最后补工程落点**：*"所以我的 L2 不是'报错'，而是**安全拒答 + 打点 + 不写缓存**——用户侧是确定的降级话术，运维侧是可观测的告警信号。降级和暴露不是对立面，它们服务的是不同的对象。"*

### D 类 · 延伸与视野

**Q25. RAG 的瓶颈一般在哪？**
> 我的体会排序：**知识处理（分块/清洗）> 召回质量 > 重排 > 生成**。大部分团队一上来就调 prompt 和换大模型，但真正的天花板在"你能不能把正确的那一段找出来"。检索对了，生成基本不会错太远；检索错了，再强的模型也只会编得更像真的。

**Q26. 长上下文都普及了（几百 K），RAG 还有必要吗？**
> 有必要。① 成本：你不可能每次问答都塞 2570 篇手册；② 延迟：长上下文的 attention 开销是超线性的；③ 精度："大海捞针"问题——信息塞得越多，模型越容易忽略中间部分（lost in the middle）；④ 溯源：长上下文无法告诉你答案来自哪一段。**RAG 和长上下文是互补的，不是替代关系。**

**Q27. 如果知识库扩大 100 倍（200 万块），你的架构哪里要改？**
> ① 索引：IVF_FLAT → HNSW（查询快）或 IVF_PQ（省内存），nlist 要按 `4×sqrt(N)` 重算；② 分库分集合：按科室/来源做 partition 或分集合；③ 检索：必须加 metadata 预过滤（先按科室筛掉 90%）；④ 缓存：命中率会成为核心指标；⑤ 入库：离线链路要支持断点续传和增量。

**Q28. 你怎么防止医疗场景的幻觉？**
> 分层防御：① 检索端——混合检索 + 重排，保证上下文是对的；② Prompt——明确"只基于提供的上下文回答，信息不足就说明"；③ 输出——带 sources 供用户核验；④ 兜底——**L2 安全拒答，检索为空时不调 LLM**（见 §3.10）；⑤ 产品——强制"仅供参考，不能替代专业医疗建议"免责声明；⑥ 评估——faithfulness 指标持续监控。
> 加分：*"但 RAG 只能降低幻觉，不能消除。真正上线还需要人工审核机制和转人工通道。"*

### 项目主线与真实性

#### 9.4 完整 RAG 流程

> 整体架构分离线建库和在线问答两大块：
>
> **离线侧**：接收 Markdown 文档 → 清洗（去导航/广告/版权/重复行）→ 父子分块（父 2000 / 子 400，overlap 60）→ BGE-M3 向量化（dense 1024 + sparse 词权）→ 写入 Milvus（IVF_FLAT 索引 + SPARSE_INVERTED_INDEX）
>
> **在线侧**：FastAPI 接收问题 → Redis 缓存命中直接返回 → 未命中进 FAQ 快通道（MySQL + jieba BM25，softmax 归一化后阈值 0.85）→ 未命中进 RAG 深通道：BERT 意图分类（general 直答 / medical 进 RAG）→ LLM 从 direct/HyDE/子查询/回溯四种策略选一 → BGE-M3 混合检索并**下推子块过滤**（chunk_type=='child'）→ Top-16 子块 → 按 parent_id 回溯去重父块 → BGE-reranker 对最佳命中子块证据打分、选 Top-2 完整父块 → 拼上下文 → LLM 生成带来源答案 → 写 MySQL 多轮 → 写 Redis 缓存

#### 9.5 为什么不用纯搜索 / FAQ / 微调

> - **纯搜索（BM25/ES）**：解决不了语义相近但表述不同的问题（"偏头疼" vs "偏头痛"），也处理不了口语化输入
> - **FAQ**：只能覆盖高频标准问题，我们的 210 题评测集里很多是长尾复杂问题，FAQ 命中率有限——所以 FAQ 是第一通道但不是唯一通道
> - **微调**：成本高且不适用于当前场景（我们不是要做领域专属模型，而是要保证答案**可溯源**）；而且微调模型的知识截止日期固定，无法随手册更新即时生效
> - **RAG** 是目前唯一能同时满足"答案有据可查"+"知识可更新"+"成本可控"三个约束的方案

#### 9.6 你具体负责什么

> 我的工作不是只调一个 Prompt，而是围绕「资料治理 → 查询分流 → 检索 → 可信生成 → 工程交付 → 评测」全链路推进：
> - **独立负责**：离线知识库构建（清洗/父子分块/向量化/入库）、检索链路设计与调参（混合权重/过滤下推/Small-to-Big）、Ragas 评估体系（210 题测试集、缺失项恢复、逐指标 judge 来源、badcase 归因和 grounded answer 迭代）
> - **参与设计**：路由与缓存策略（FAQ 第一通道重构）、Prompt 工程（grounding 忠实度优化）
> - **协同完成**：Streamlit 前端与 FastAPI 接口联调

#### 9.7 项目最难的问题是什么

### 数据预处理与切块

#### 9.9 给你 Markdown 文档，如何从零设计 RAG

> 先判断文档类型和噪声水平（手册 HTML 里混着导航链接、版权声明、分页符）→ 用 document_loader 多格式解析 → data_cleaner 清洗（去噪/抽取标题来源）→ chunk_splitter 父子分块（父 2000 / 子 400，overlap 60）→ embedding_provider 向量化（BGE-M3 一次前向出 dense+sparse）→ milvus_store 入库（建索引/分批 insert）→ 在线链路接 LLM 生成 → 最后用 Ragas 做四指标评估闭环。

#### 9.10 数据来源、规模和格式

> 知识源是《默沙东诊疗手册（大众版）》，公开公益科普材料，无商业诊疗导向。清洗后 **2570 篇 Markdown**，父子分块后 **20816 个文本单元**（子块 16880 + 父块 3936）。平均每块 462–555 字符，最大 1998 字符。

#### 9.11 如何切块？为什么 400 / 2000？

> 这是**小粒度检索精度 vs 大粒度生成完整性**的 trade-off：
> - **400 字子块**：语义聚焦、检索精准，但 LLM 拿到的上下文残缺
> - **2000 字父块**：上下文完整，但一个向量编码多个主题，检索精度下降
> - **overlap 60**：防止单个医学论点被切断在块边界（约一个中文句子长度）
> - **父子方案**：用小的去检索（精度），用大的去生成（完整），空间换时间

#### 9.12 为什么用 Parent-Child 而不是固定分块

> 固定分块没法兼顾精度和完整性。父子分块的核心优势是**解耦**：检索粒度和生成粒度独立控制。而且父块正文冗余存进子块的 parent_content 字段，避免回查时的串行依赖（一次 Milvus 查询 ~10ms，但按 parent_id 回查是串行的，在线链路里翻倍延迟）。

### Embedding、向量库与检索

#### 9.13 为什么选择 BGE-M3

> 三个原因：① **一次前向同时出 dense(1024维) + sparse(词权字典)**，省掉单独维护 BM25 索引；② 中文医学语义表现好（CT、HbA1c 这类中英混排术语是强项）；③ **本地部署**，20816 块向量化不依赖外部 API。对比 m3e：m3e 只有 dense，需要额外配 BM25 才能做混合检索。

#### 9.14 为什么用 Milvus 不用 FAISS / ES / pgvector

> - FAISS：偏向本地小规模，缺少 metadata 过滤、持久化和生产运维能力
> - ES：全文检索强但不是专业向量数据库，向量检索性能和功能都不如原生方案
> - pgvector：PostgreSQL 插件，检索性能和功能受限
> - **Milvus**：专业向量数据库，支持混合检索（dense+sparse）、metadata 过滤下推、持久化、分布式扩容——2 万条当前规模用 IVF_FLAT 就够，涨到百万级换 HNSW 或 IVF_PQ 即可

#### 9.15 dense 和 sparse 各解决什么问题

> - **Dense（稠密向量）**：解决语义相似问题——"偏头疼"="偏头痛"、"布洛芬"="芬必得"
> - **Sparse（稀疏词权）**：解决字面精确匹配问题——"1 型糖尿病" vs "2 型糖尿病"字面极近但语义相反，必须靠关键区分词
> - 两者是**正交能力**，缺一个就有一类 query 会挂。BGE-M3 一次前向同时出两种，省掉"两个模型拼"的额外链路

#### 9.16 混合检索的权重怎么定的

> dense 1.0 / sparse 0.7，**对齐 EduRag 初值后在医疗语料上人工调的**。Milvus 的 WeightedRanker 做的是**分数归一化后加权求和**（不是原始分乘权重）。诚实地说：没有做系统的网格搜索或 A/B 对比，更严谨的做法是构造带标注的召回评测集用 Recall@K 搜参或换 RRF 规避量纲问题。**这是我知道的可优化点，不会编"实验得出最优"。**

#### 9.17 为什么需要 rerank

> BGE-M3 是**双塔（Bi-Encoder）**：query 和 doc 各自独立编码，只在最后算余弦，**无交互**，精度有上限。BGE-reranker 是**单塔（CrossEncoder）**：query 和 doc 拼接后一起过 self-attention，每对 token 都能看到对方，精度高但**必须在线算**（无法预编码）。所以两阶段是精度与成本的唯一解：用便宜的召回从 2 万缩到 Top-16 子块 → 回溯成 3-5 个父块 → 再用贵的重排收到 Top-2。

#### 9.18 topK / topN 怎么定

> topK（粗排 16）负责别漏——宁可多召几个；topN（精排 2）负责别给太多——LLM 的上下文窗口和注意力有限，塞太多无关段落会稀释注意力。实际调试时如果发现答案不完整就考虑增大 topK，如果发现答案里有无关内容就减小 topN。

### 路由、降级与安全

#### 9.19 FAQ + RAG 如何路由

> **所有问题先过 FAQ 第一通道**（不是先分类再决定）：Redis 缓存 → MySQL + jieba BM25 → softmax 归一化 → 阈值 0.85 → 命中即返（零 LLM 调用）。未命中才降级进 RAG 深通道（BERT 意图分类 → LLM 选检索策略 → ...）。
>
> 这个架构是从一个 badcase 反推出来的：原来 FAQ 是"意图分支"里的一个选项，BM25 阈值失效导致"头痛"被误匹配到"声带息肉"。修好评分尺度（softmax 归一化）后，FAQ 提升为第一通道，同时简化了整条路由。

#### 9.20 分类错了怎么办

> 保存分类结果、置信度和实际 route 到日志；用标注集看混淆矩阵。**高风险错误是把医疗问题分到通用回答**（比反过来危险得多），所以未知状态默认走医疗受约束路径（RAG + grounding 约束）。另外我们的 BERT 分类器只有 2 类（general/medical），acc=1.0 但验证集与训练集同源（模板化生成），**真实线上准确率可能偏低**——这是我会主动承认的点。

#### 9.21 检索不到怎么办（🟢 加分题，务必主动讲）

> **先亮原则**：*"降级路径必须比主路径更安全，而不是更粗糙。"*
>
> **三层降级**：
> - **L0 正常**：严格 Small-to-Big，chunk_type 过滤下推只召回子块
> - **L1 子块为空**：**同粒度降级**——放开过滤重查，命中父块后在内存里切成 400 字子块再返回（输出粒度不变，只是换了检索入口）
> - **L2 仍为空**：**安全拒答**——固定话术 + **不调用 LLM**（医疗场景无依据硬答是风险最高的行为）
>
> **两个反直觉取舍**：
> - L1 没有"直接返回 2000 字父块"——那是拿质量下降伪装成降级：既稀释注意力、翻倍 token，又掩盖数据问题。**这条路径永久禁止、无开关。**
> - L2 没有"让 LLM 兜底"——它会编而且语气权威，用户分不清。宁可拒答引导就医。

#### 9.22 RAG 如何减少幻觉

> 三层防御：
> ① **检索端**：混合检索 + reranker 保证上下文是对的
> ② **Prompt 端**：线上生成链路已落地 grounding 硬约束（系统提示明确"只能使用检索上下文、禁止引入任何外部医学知识、不足即拒答"，由 `LLM_GROUNDING` 开关控制，默认开启）
> ③ **兜底端**：L2 安全拒答，检索为空时不调 LLM
> ④ **评估端**：持续监控四指标。最新完整报告为 F=0.8163、AR=0.5007、CP=0.8405、CR=0.7619；同时保留逐项 judge 来源
>
> 本质：**先把证据找准，再限制模型按证据回答，证据不足就不回答。**

#### 9.23 如何判断幻觉发生在召回还是生成

> 用 request_id 日志把阶段串起来：正确证据是否入库 → 是否进入 topK → 是否被 rerank 保留 → 是否进入 Prompt → 答案是否违背证据。**没找到证据是召回问题，找到证据还乱答才是生成幻觉。** 我们的评估体系（Ragas 四指标）正好提供这个归因坐标：context_recall 低 = 检索漏召；faithfulness 低 = 生成幻觉。

#### 9.26 如果让你再做一遍，优先改什么

> ⑤ **流式输出暴露**（`generate_stream` 已有，API 层没接）

### 模型基础与工程

#### 9.27 Transformer / 自注意力 / BERT vs BGE

> Transformer 用自注意力建模 token 间关系：Q·K^T 缩放 → softmax → 加权 V。多头从不同子空间捕捉关系。
>
> **BERT 不能直接替代 BGE**：BERT 的预训练目标（MLM/NSP）不是 query-passage 检索相似度，直接取向量未必适合检索；BGE 经过**对比学习**和检索任务微调，对 query 指令、池化和归一化有明确约定。不是不能用，而是需要证明——我们就是用评测数据证明 BGE-M3 比 BERT 更适合这个场景。

#### 9.28 temperature / top_p / top_k

> temperature 控制概率分布平滑度：低→稳定确定，高→多样随机。**裁判用低 temperature（0.01）保一致性，生成用中等温度（0.2-0.5）平衡质量和多样性。** top_p / top_k 是核采样方式，在生成端使用。但对我们项目来说，**证据门控和检索质量对最终答案的影响远大于这些采样参数**——检索对了，生成基本不会差太远。

#### 9.29 高并发怎么处理

> FastAPI 的 `def` 路由跑在**线程池**（默认 40 线程）。瓶颈在 GPU 侧（BERT 推理和 reranker 串行）和外部 LLM API 延迟。优化方向：① 缓存前置挡掉大部分请求（Redis TTL 1h）；② BERT 意图分类与 Redis/FAQ 查询**并行**（无数据依赖）；③ embedding 做 batch 聚合；④ GPU reranker 换轻量模型或走异步队列；⑤ 流式输出改善感知延迟。

#### 9.30 一句话总结项目亮点

> 这个项目的亮点不是"用了 RAG"，而是：**把"答案可溯源"这件事工程化了**——父子分块解耦精度与完整性、混合检索兼顾语义与关键词、三层降级降低无依据作答风险、评测报告保留缺失项与逐指标 judge 来源，以及从"头痛误匹配声带息肉"这个 badcase 反推出整套路由重构。**最有价值的部分不是搭起来了，而是我把它每个环节拆开看过、量过、改过。**

### 补全章节（覆盖 FN_RAG 其余高频题，全部适配 med_rag）

#### 9.34 客户/导师觉得效果不好，但工期到了怎么办（项目主线）

> 先把"效果不好"拆成：检索错位 / 召回不足 / 答案遗漏 / 相关性低 / 延迟高 / 范围变化，用 request_id 日志复现具体样例。已承诺范围先交付可用闭环（FAQ 快通道 + 单点科普查询 + 来源展示）；高风险或证据不足问题启用 L2 拒答和人工兜底。对未解决问题给失败样本、影响范围、临时降级和迭代时间，并提前对齐验收口径。我不承诺 100% 准确，而是对齐来源正确率、步骤完整性、无答案识别率和 P95 延迟这些可验证指标。【已验证：L2 拒答已实现】

#### 9.35 表格、图片和跨页表怎么处理（数据预处理）

> 当前《默沙东手册》是 Markdown 结构化文本，表格以 Markdown 表格存在，data_cleaner 会保留表格结构；图片类内容（解剖图等）目前不在检索范围（手册大众版以文字为主）。【推断：若引入带图 PDF，需 OCR + 表格结构识别，可接 rapidocr / 表格专用解析】。跨页表格按表头连续性做合并。诚实说：本项目未做复杂扫描件 OCR，这是已知边界。

#### 9.36 数据更新和脏数据如何处理（数据预处理）

> 更新走"重新入库"而非原地改：新文档再次经过 清洗→分块→向量化→入库 流程，构建新集合，测试通过再切换别名。脏数据（空文件、重复、乱码、清洗失败）不进库，记录后重新处理。当前用 Milvus 集合别名做发布切换，回滚即切回上一版。【详见 9.53】

#### 9.37 FLAT / IVF / HNSW 索引怎么选（Embedding/向量库）

> 当前 20816 块用 **IVF_FLAT**（精确聚类召回，规模小够用）。原则：先用高精度 baseline，再按数据量/内存/QPS/目标 Recall 压测调参。涨到百万级换 **HNSW**（快、召回高、吃内存）或 **IVF_PQ**（量化省存储、略损精度）。FLAT 适合小数据建召回基准。稀疏向量用 **SPARSE_INVERTED_INDEX** 独立建。不背固定参数，按压测说话。【已验证：IVF_FLAT + SPARSE_INVERTED_INDEX 已建】

#### 9.38 MySQL、Redis、Milvus 如何分工（Embedding/向量库）

> **Milvus** 存向量 + chunk 文本 + metadata（doc_id/parent_id/来源/标题）；**MySQL** 存 FAQ 正本、用户多轮对话、构建任务与发布记录、审计；**Redis** 存问答缓存（TTL 1h）和会话。可概括：Milvus 做语义检索，MySQL 记事实与发布，Redis 加速共享。原文 Markdown 留在受控文件存储。

#### 9.39 Milvus 是否只存向量，原文在哪里（Embedding/向量库）

> 不止向量。Milvus 存 **向量 + 检索所需文本 + metadata**（doc_id、parent_id、doc_name、chunk_type、source）。原始完整 Markdown 放在文件存储，Milvus 只保留召回和生成所需的片段，避免大文档撑爆向量库。

#### 9.40 BM25、Milvus 混合检索和 RRF 的关系（检索/融合）

> 三者不同层次：**BM25（jieba 分词）** 负责 FAQ 文本精确匹配（第一通道）；**Milvus 混合检索** 用 BGE-M3 的 dense+sparse 双路召回专业知识；若未来做 Multi-Query/Decompose 多分支召回，再用 **RRF** 按排名融合。当前我们 FAQ 用 BM25、专业知识用 Milvus 混合，尚未引入 RRF（单 query 足够）。【推断：多子查询时再加 RRF】

#### 9.41 检索不准如何定位（检索/融合）

> 按链路顺序定位：数据清洗→分块→向量化→召回(topK)→过滤下推→rerank→生成。具体看 request_id 日志串起每个阶段：正确证据是否入库、是否进 topK、是否被 rerank 保留、是否进 Prompt、答案是否违背证据。没找到证据=召回问题，找到还乱答=生成问题。我们的 Ragas CP/CR 也提供间接坐标。

#### 9.42 Rerank 分数能当概率吗（检索/融合）

> 不能。Reranker 分数只用于同一候选集内排序，不同模型/请求/数据分布标度不一致。若要用统一阈值，必须在验证集上校准并分析误拒/误答成本。我们当前 reranker 只取 Top-2，不依赖绝对分数做门控（门控靠 L0/L1/L2 证据存在性判断）。

#### 9.43 Query 改写为什么需要多种策略（检索/融合）

> 目的让口语化问题更适合检索。我们有 LLM 从 direct/HyDE/子查询/回溯 四策略选一；还可扩展：表达不规范做 Rewrite，多条件拆子问题，模糊问题扩写相近问法。关键约束：**不能改丢原问题的实体、数值、否定条件**（否则反而伤召回）。这是下一步重点（见 9.26 ③）。

#### 9.44 Fast / 复杂问题如何路由（无 Chunkless，用 Small-to-Big 适配）（路由）

> FN 的 Chunkless 适合跨章节归纳，我们当前用 **Small-to-Big（父子块）** 覆盖：简单单点事实走子块精确定位；需要完整上下文的走父块。若未来遇到"比较两种病/完整流程"类跨章节问题，可扩展 Chunkless（文档级导航收集证据节点），当前未实现，作为可选演进。【诚实：未做 Chunkless】

#### 9.45 短问题"查一下这个" / 多轮指代（路由）

> 当前 session 主要用于关联，多轮靠最近 3 轮 history 拼进 Prompt（rag_system 取 history[-3:]）。短问题"查一下这个"会结合最近对话做指代补全，补不出就追问（如"请问具体想了解哪种疾病？"），不让模型硬猜。身份/权限每轮由服务端会话获取，不依赖模型记忆。【推断：更成熟的多轮需实体槽位追踪，列为下一步】

#### 9.46 上下文太长或用户换话题怎么办（路由）

> 不把全部历史原样拼进 Prompt，只保留最近关键轮次 + 结构化实体摘要；检测到业务对象明显变化时清理旧槽位。当前输入可更新查询条件，但不能覆盖权威医学事实或提升权限。高风险信息（剂量、禁忌）需再次确认。一句话：**太长就截断筛选摘要，换话题就重建当前上下文。**

#### 9.47 MCP 和 Function Calling 的区别（路由/工具）

> Function Calling 是模型按 schema 选工具生成参数；MCP 是把工具/资源/提示标准化暴露给客户端的协议，二者可组合（MCP Server 暴露工具，模型按 schema 调用）。无论哪种，权限/参数校验/超时/重试/审计必须由服务端控制，不信模型文本。本项目未接入外部工具/MCP，仅内部 FAQ/检索/LLM，边界清晰。【诚实：未做 MCP】

#### 9.48 如何防提示词注入（安全）

> 外部文档与用户输入都视为不可信：检索内容与系统提示分区，工具权限由后端 RBAC + 参数校验控制。知识库外或要求编造内部规定的走拒答；敏感接口需管理员身份。输入输出做安全检测与审计，不只靠"忽略注入"一句 Prompt。医疗场景额外强调：任何试图让模型输出诊断/药方的指令都被重定向到科普+就医引导。

#### 9.49 多租户和文档权限怎么做（安全，适配医疗公开库）

> 当前知识库是**公开医学科普**（默沙东手册），无用户私有文档，所以不存在细粒度 ACL；所有用户共享同一公开 KB，权限只区分普通用户/管理员（后者管入库与发布）。若未来接入机构私有库，需在 chunk 写 tenant_id/kb_id/role 并在认证后作为 Milvus metadata filter 与检索同时执行，不能先全库召回再让模型忽略。【诚实：当前无多租户，设计已想清楚】

#### 9.50 RAG 回答慢怎么优化（性能部署）

> 先拆分各段耗时：FAQ/意图/BERT/embedding/Milvus/reranker/首 token/完整生成。当前真实瓶颈是 **CPU 跑 torch（BERT 意图 + BGE reranker 串行）** 和**外部 LLM API 延迟**。优化优先级：① 高置信 FAQ/规则减少 LLM 调用；② 可并行的改写与召回并行；③ 缓存热点问题与检索结果（Redis）；④ 按意图动态缩 topK；⑤ GPU/轻量 reranker；⑥ 流式输出改善感知延迟。P95 未达标我不回避。

#### 9.51 为什么用 FastAPI 和 Docker Compose（性能部署）

> FastAPI 适合 Python 模型服务：类型校验、异步、依赖注入、OpenAPI 齐全。Docker Compose 统一拉起 Milvus/Redis/MySQL 等依赖，减少环境差异。当前是功能化单体，不为形式拆微服务；当模型推理/入库/问答需要独立扩缩容时再按瓶颈拆。【已验证：FastAPI 8005 + Streamlit 8501 + Redis + MySQL 已跑通】

#### 9.52 线上出问题怎么排查（性能部署）

> 从 request_id 对齐请求/应用/依赖日志，再看健康探针、容器状态、资源、环境变量、镜像与依赖版本、挂载、网络/DNS、模型服务、Milvus、MySQL、Redis。本地正常线上异常优先比配置与依赖。LLM 空响应/瞬时失败自动重试，最终失败返稳定错误；reranker 异常保留原召回顺序避免链路不可用。

#### 9.53 知识库更新如何发布（影子集合 / 灰度）

> 设计上用**集合别名 + 影子集合**：先构建唯一命名的新集合，全部写入成功再切 active 别名，失败则当前集合不受影响；MySQL 记构建任务与发布关系，回滚切回上一版。诚实说：当前规模下更新靠重新入库+别名切换已实现基础版，完整灰度发布流水线是可演进项。【适配 FN 46，已部分落地】

#### 9.54 如何分层评估 RAG（检索 / 答案 / 系统三层）（评测）

> 三层：① **检索层** Recall@K / MRR / NDCG，看正确证据是否召回；② **答案层** 正确性、faithfulness、answer relevancy、来源正确性、步骤完整性（医疗额外看剂量/禁忌是否遗漏）；③ **系统层** P50/P95、失败率、拒答准确率、任务完成率。测试集覆盖口语/错别字/单点/跨章节/无答案/注入攻击。我们 Ragas 四指标覆盖答案层 + 部分检索层（CP/CR），系统层延迟用压测补。【详见 9.24/9.25】

#### 9.55 为什么 30/210 题样本不够，后续怎么扩展（评测）

> Ragas 210 题是算法指标样本，业务验收还需更大分层集。后续：① 扩到 500+ 题按疾病系统/急症/慢病/用药/无答案分层，设近邻混淆题；② 评测集与开发集隔离，改完既跑目标 badcase 也跑全量回归；③ 业务层补充"是否引导正确就医/是否遗漏禁忌"人工标注。诚实说：当前未做生产级业务验收评测。

#### 9.56 如何评估业务价值（评测）

> 若上线试点，用传统查手册 vs 系统自然语言查询交叉对照，记资料定位中位耗时、任务完成率、来源命中率、无答案识别率、误答率。评分规则上线前固定，不事后挑有利指标。当前无生产收益数据，不编造"效率提升 X%"。【诚实：价值未经生产验证】

#### 9.57 面试官可能继续追问的风险点（反向追问·诚实边界）

> - **"2570 篇是否真实？"**——是清洗后实际入库数，可现场核对 `_source`。
> - **"是否做诊断/开药方？"**——否，只科普，红线不碰。
> - **"是否接核心医疗系统？"**——否，纯知识问答，不执行医疗操作。
> - **"准确率是不是 0.7299？"**——不是。0.7299 是当前 Ragas 四指标加权综合，非临床准确率；报告以 GLM-4.6V 为主裁判，少量缺失项由 deepseek-v4-flash 补齐。
> - **"为什么这么慢？"**——CPU 跑 torch + 外部 LLM 延迟是瓶颈，已有优化顺序。
> - **"多轮记忆/多租户/MCP 是否完成？"**——当前部分实现，生产化设计已想清，不夸大。
> - **"grounding 全量复测做了吗？"**——**做完了，而且是两轮**：离线轮 glm-4.7 裁判 / 210 题 / F 0.259→0.464（ΔF+0.21）；**线上轮走真实服务链路重生成 210 题 + glm-4.5-air 裁判 / 207 题有效 / F 0.713→0.964（ΔF+0.25），AR 0.841→0.698，加权综合 0.687→0.714**。两轮裁判不同、链路不同，ΔF 均落在 +0.21~+0.25。见 9.24/9.26。
