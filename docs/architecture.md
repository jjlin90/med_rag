# 医疗 RAG 问答系统 — 整体架构设计

## 一、架构总览

本系统采用**离线数据预处理 + 在线检索生成**的分离架构，把「知识库构建」与「推理服务」彻底解耦，
规避传统 RAG 在医疗场景下的上下文断裂、召回噪声、幻觉严重、回答不严谨等痛点。

整体链路：

```
原始医疗数据(HTML)
   → 清洗结构化(Markdown)
   → 父子分层分块
   → BGE-M3 向量化(稠密+稀疏)
   → Milvus 入库
   ───────────── 离线 ─────────────
   用户提问（双通道架构，对齐 EduRAG）
   → ① FAQ 快通道（优先）
        Redis 缓存命中 → 直答
        → 未命中走 MySQL + jieba BM25，得分 softmax 归一化（阈值 0.85）
        → 达标直答并写回 Redis；不达标自动降级 ②
   → ② RAG 深通道（降级路径）
        → BERT 意图分类（general / medical，全程仅跑一次）
        → LLM 自动选检索策略（直接检索 / HyDE / 子查询 / 回溯抽象）
        → Milvus 混合检索（稠密+稀疏 WeightedRanker 融合，Top-16）
        → Small-to-Big：Top-5 子块命中 → parent_id 聚合父块
        → BGE-reranker 对每个父块的最佳命中子块精排 → 返回 Top-2 完整父块
        → 医疗专属 Prompt + 多轮历史组装
        → LLM 严谨生成
   → 写入 MySQL 会话历史（按 session_id，保留最近 5 轮）
```

> **分层降级策略**（retrieval.py）：检索侧按 L0 → L1 → L2 逐级兜底——
> L0 严格 Small-to-Big（chunk_type 过滤下推，orphan 父块打点剔除）；
> L1 同粒度降级（子块召回为空时放开过滤重查，命中父块现场切成 400 字子块，粒度不退化）；
> L2 安全拒答（固定话术，不调用 LLM，避免参数知识编造）。
> 核心原则：降级路径必须比主路径**更安全**，而不是更粗糙。

> 在线问答的「意图分类 → 策略选择 → 检索与合并 → 重排序 → 构建上下文 → LLM 生成」
> 六步主流程统一封装在 `src/online_service/rag_system.py` 的 `RAGSystem` 类中（对齐 EduRAG 主流程），
> 由 FastAPI 层（`main_api.py` 的 `RAGWebAPI`）组装缓存 / FAQ / 会话 / 评估等外围能力。

## 二、各层级详细设计

### 1. 数据预处理层（离线）

针对默沙东大众版原始 HTML 资源做深度清洗归一化，解决原生网页冗余、格式混乱、无效内容干扰问题。

- 剔除无效模块：导航栏、侧边栏、页脚、版权声明、作者信息、修订日期、自测习题、广告外链、英文冗余资料。
- 过滤无效文本：零散短句、纯数字、无意义标注、页面跳转提示。
- 结构化重构：识别疾病章节、标准化标题分层、规整段落空行与排版。
- 产出：约 **2570 篇**高质量、无噪声、结构统一的 Markdown 医疗知识库（`data/clean_md/`）。

### 2. 文档分层切片层（核心优化点）

摒弃固定大小随机切分，采用**父子双层分块**（`chunk_splitter.py`），适配医疗长文本。

- **子块（检索块）**：400 字符细粒度切片，保留局部细节语义，用于向量检索，提升召回精准度。
- **父块（上下文块）**：2000 字符完整段落，保留疾病整体逻辑（病因、症状、治疗体系），用于 LLM 生成阶段补全全局上下文。
- 切片重叠 60 字符，规避语义割裂与关键信息截断。

当前 `data/split_docs/docs.json` 共 **20816 条记录**，按 `parent_id` 语义统计为 16880 子块 + 3936 父块。该存量文件生成于父块 `chunk_type` 修复前，顶层 `chunk_type` 值不可用于统计；重新执行离线分块后，新文件会正确写入 `parent` / `child`。

### 3. 向量化与混合检索层

这是本系统检索质量的关键，由 `embedding_provider.py` + `milvus_store.py` 实现。

**双模态向量（BGE-M3）**：
- **稠密向量（dense, 1024 维）**：编码文本深层语义，擅长口语化问诊、模糊提问、同义改写的召回。
- **稀疏向量（sparse, lexical weights）**：BGE-M3 一次前向同时产出的词项权重（类似 BM25 的词项重要性），擅长医疗专业关键词（如「胰岛素」「糖化血红蛋白」）的精确命中。

> 说明：向量库中的「稀疏向量」来自 BGE-M3 的 lexical weights，并非独立 BM25；
> 项目另有一套基于 jieba 的 BM25，用于 **FAQ 直答**（`faq_search.py`），与向量库稀疏检索是两路不同用途。

**Milvus 混合检索**：
- 同一集合存储 dense + sparse 两个向量字段，dense 用 IVF_FLAT 索引、sparse 用倒排索引。
- schema 顶层含 `chunk_type` 字段，检索时过滤下推（新库 `chunk_type=='child'`，旧库自适应为
  `parent_id != ""`），保证父块不抢占召回槽位。
- 查询时用 `MilvusClient.hybrid_search` 对两路分别 ANN 检索，再用 `WeightedRanker` 按
  `SPARSE_WEIGHT=0.7` / `DENSE_WEIGHT=1.0` 加权融合，去重排序。

### 4. 重排优化层

初筛候选片段含低相关/冗余/噪声，经 **BGE-reranker-large**（`reranker.py`，FlagReranker 交叉编码）精细筛选：
- 检索链路：Top-16 粗排召回 → Top-5 子块命中 → `parent_id` 聚合父块 → 用每个父块的最佳命中子块精排 → 返回 **Top-2** 完整父块用于生成。
- 对「查询-候选片段」逐对打分、全局排序，过滤无关与重复内容，精简送入 LLM 的上下文，降低幻觉与 Token 消耗。

### 5. LLM 生成层

定制**医疗领域专属 Prompt**，约束生成逻辑：
- 严格依赖检索上下文生成，禁止编造医疗知识。
- 回答结构化、分点清晰、通俗易懂。
- 未知内容如实告知，杜绝虚假诊疗建议。
- 温度调低（0.2），保证严谨、低随机。

兼容任意 OpenAI 兼容接口（智谱、通义千问、本地开源模型等），通过 `.env` 的
`LLM_API_KEY` / `LLM_BASE_URL` 切换。

### 6. GPU 加速与工程化

- 设备自动检测：`DEVICE = cuda if torch.cuda.is_available() else cpu`，向量化与重排自动上 GPU（fp16）。
- 向量化批处理对显存做防碎片处理（每批 `torch.cuda.empty_cache()`），避免长跑时显存顶格导致的骤降。
- 离线全量入库（约 20816 块）在 RTX 4060 上约 **30 分钟**（纯 CPU 需十余小时）。

## 三、核心技术优势

1. **数据质量高**：全量清洗网页噪声，构建纯净结构化医疗知识库。
2. **切片策略优**：父子分层分块，兼顾检索精度与上下文完整性。
3. **检索能力强**：BGE-M3 稠密+稀疏双模态加权融合，适配专业词与口语化双重提问。
4. **回答更严谨**：重排过滤噪声 + 医疗专属 Prompt，抑制幻觉。
5. **工程规范化**：模块化解耦、统一配置、环境隔离、GPU 加速、可复用可迭代。

## 四、应用场景

- 大众日常慢病自查、健康知识科普咨询。
- 常见疾病症状、病因、治疗、护理、并发症答疑。
- 家庭健康管理、用药与康复常识科普。

**仅限科普学习，不支持临床诊疗。**
